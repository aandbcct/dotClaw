# dotClaw Wiki 编写规范与验收准则

> 适用范围：`docs/wiki/README.md`、各模块 Wiki，以及后续独立机制或 ADR 文档。  
> 文档目的：统一后续 Wiki 的信息结构、章节职责、表达深度和验收标准，防止文档再次退化为目录清单、修改手册、机械模板或互相冲突的重复说明。  
> 基准方向：以当前 Tool 模块完整型文档（v1 方向）为基准，只允许在不破坏总体性和完整性的前提下局部优化。

---

## 1. 文档体系的总体分工

### 1.1 README 与 Wiki 的职责不同

根 README 负责项目叙事和对外展示，主要面向招聘者、面试官、新用户和首次了解项目的人。它回答：

- dotClaw 是什么；
- 为什么需要它；
- 系统采用什么总体分层；
- 一次请求如何经过系统；
- 项目完成了哪些重要工程设计；
- 当前能力和边界是什么；
- 如何快速启动；
- 去哪里继续阅读。

Wiki 负责开发者代码地图和架构理解，主要面向准备阅读、修改、扩展或排障代码的人。它回答：

- 项目有哪些逻辑模块；
- 模块在系统中的位置；
- 模块内部有哪些组件；
- 组件里有哪些核心类和协议；
- 模块、组件和类之间如何依赖、调用和协作；
- 关键流程如何运行；
- 设计为何这样选择；
- 当前有哪些痛点和演进方向；
- 源码在哪里。

**禁止把 README 写成详细代码手册，也禁止把 Wiki 压缩成 README 式项目简介。**

### 1.2 Wiki 首页与模块 Wiki 的职责不同

Wiki 首页负责全局代码地图，不负责展开单个模块的全部细节。首页应提供：

1. 项目代码地图；
2. 系统核心链路；
3. 逻辑子系统与模块索引；
4. 模块依赖关系；
5. 常见修改入口；
6. 推荐阅读路径；
7. 当前架构边界。

模块 Wiki 负责一个模块的完整、自包含说明。它不能只写一句“详见其他模块”，也不能要求读者先读完所有相邻模块才能理解当前模块。

### 1.3 单一主归属不等于禁止重复

同一个事实应有一个完整、权威的主归属文档；其他文档可以为了理解当前模块而保留摘要和必要上下文。

例如审批机制：

- Tool 文档完整说明：为什么本次 Tool Call 会产生 `allow / ask / deny`，Tool 如何判断是否需要审批；
- Runtime 文档完整说明：审批如何持久化、暂停、恢复和收口；
- Channel 文档说明：用户决定如何被收集和提交。

三个文档都可以出现审批流程，但侧重点必须不同，不能复制同一段文字，也不能互相产生冲突。

## 2. Wiki 编写的核心目标与优先级

模块 Wiki 的首要目标不是“让开发者最快改代码”，而是建立完整、稳定、自顶向下的代码认知。

优先级如下：

```text
理解模块在系统中的位置
→ 理解模块包含哪些逻辑组件
→ 理解组件包含哪些核心类和协议
→ 理解组件、类和相邻模块如何依赖与协作
→ 理解关键运行流程、设计取舍和边界
→ 最后定位常见修改入口和源码文件
```

因此：

- 修改入口应保留，但不是文档组织主轴；
- 源码目录应保留，但只能作为逻辑说明后的物理索引；
- 不得为了缩短篇幅而删除跨模块上下文、重要支持机制或设计细节；
- 不得把模块写成孤立的类清单；
- 不得把模块 Wiki 改造成任务卡、操作手册或表格集合。

---

## 3. 模块文档的固定总体结构

各模块 Wiki 原则上采用以下九个章节：

```text
1. 模块定位与边界
2. 模块在项目中的位置
3. 组件总览
4. 各组件的类与职责
5. 组件依赖和使用流程
6. 对外接口与数据契约
7. 常见修改入口
8. 设计取舍、痛点和演进方向
9. 源码索引
```

这是信息顺序约束，不是死板排版约束。简单模块可以缩短章节，复杂模块可以增加三级标题，但不能改变自顶向下的总体认知路径。

### 3.1 为什么采用这套顺序

- 第 1～2 节先建立系统坐标；
- 第 3 节建立模块内部地图；
- 第 4 节进入核心类和实现内容；
- 第 5 节把静态结构还原为真实协作；
- 第 6 节明确稳定边界；
- 第 7 节在读者理解架构后给出开发入口；
- 第 8 节解释设计判断和未完成问题；
- 第 9 节再映射回物理文件。

**禁止直接从源码树开始写，也禁止先写“如何修改”再补架构。**

## 4. 各章节的内容契约

## 4.1 模块定位与边界

本节回答：

- 模块解决什么工程问题；
- 对外提供什么稳定能力；
- 主要被谁使用；
- 明确不负责什么；
- 哪些职责属于相邻模块。

推荐内容：

- 一段准确的模块定位；
- 3～7 项核心职责；
- 3～7 项非职责；
- 必要的入口和适用边界。

本节不应：

- 罗列完整类清单；
- 解释全部历史；
- 展开完整流程；
- 提前塞入大量源码文件；
- 使用空泛表述，例如“负责工具相关功能”“提供核心能力”。

模块定位应能区分：

```text
它为什么存在
它对外提供什么
它与相邻模块如何分工
```

## 4.2 模块在项目中的位置

本节建立模块与整个系统的关系。

至少应说明：

- 直接上游是谁；
- 直接下游是谁；
- 调用方向是什么；
- 谁负责装配；
- 是否通过 Port / Adapter 接入；
- 哪些反向依赖被禁止。

模块位置图必须是**局部系统图**，而不是只画模块内部文件。

例如 Tool 文档不能只画 Registry、Executor、Broker 和 Policy，还必须出现：

```text
LLM / RuntimeEngine
→ ToolPort / ToolExecutorAdapter
→ ToolExecutor
→ ToolHandler
→ Builtin / Provider / MCP
```

否则模块会被孤立，读者无法理解它为何被调用、结果流向何处。

图后必须解释：

1. 调用发起者；
2. 模块内部协调者；
3. 依赖倒置位置；
4. 组合根；
5. 禁止的反向依赖。

## 4.3 组件总览

本节回答“模块由哪些重要部分构成”。

组件划分依据是**稳定职责和理解价值**，不是源码目录，也不是强制数量。

逻辑组件可以是：

- 一个完整子系统；
- 一组围绕同一职责协作的类；
- 一个跨目录接入边界；
- 一个重要的支持机制；
- 一个虽非独立模块、但不解释就无法理解整体的部分。

例如 Tool 中可以同时保留：

- 声明与契约；
- Schema 与参数校验；
- 发现与注册；
- 执行调度；
- Capability Broker；
- Policy 与审批；
- Builtin；
- 固定网络 Provider；
- MCP 接入；
- Runtime Adapter；
- Skill 旁路；
- Bootstrap 装配。

这些内容不一定处于同一层级，可以进一步分为：

```text
核心组件
能力实现
外部接入
辅助机制
```

但不能仅为了把组件数量压到 4～8 个而删除或强行合并重要部分。

组件总览推荐包含：

- 一张组件关系图；
- 一张组件责任表；
- 必要的层级分类；
- 图后对关键依赖方向的解释。

组件图不应：

- 直接复制源码目录；
- 展开所有类；
- 把相邻模块完全删掉；
- 与模块位置图完全相同；
- 为追求整洁而遗漏重要接入或支持机制。

## 4.4 各组件的类与职责

本节从组件逐层进入核心类、协议、DTO 和重要辅助类型。

每个组件至少应回答：

```text
组件负责什么
包含哪些核心类和协议
每个核心类负责什么
每个核心类明确不负责什么
组件依赖谁
组件被谁使用
内部如何协作
```

每个核心类、协议、数据对象或重要子部分的说明，开头必须先用 1～3 句话交代：

```text
它的职责是什么
它为什么存在或解决什么问题
它在当前组件或调用链中处于什么位置
```

不能直接从字段表、方法列表、代码片段或执行规则开始。即使标题已经写出类名，也必须先建立用途认知，再进入实现细节。

字段表和模块表还必须回答字段在系统中的真实作用。对于状态、DTO、配置、缓存和持久化对象，至少说明：

```text
字段由谁创建或写入
字段由谁读取
字段是否持久化
字段是权威事实、引用、派生值还是进程内缓存
字段参与哪个调用或恢复步骤
字段不应被用来推断什么
```

禁止只写“字段名 + 类型 + 重复字段名的中文翻译”。例如 `action: AgentAction` 不能只解释为“当前动作”，而应说明它是 Checkpoint 保存的 operation node、由状态迁移产生、由 Engine 消费，并且不是第二份运行状态。

对于一组名称相近的类型，应先增加对照说明。例如 `AgentRunEvent` 与 `RunEvent`、`ContextBundle` 与 `ContextVersion`、`Task` 与 `AgentRun`，必须明确各自的生命周期和权威边界。

表达形式不强制统一。可以根据内容选择：

- 核心类较多、职责适合比较：使用表格；
- 执行逻辑复杂：使用连续段落和局部流程；
- 安全约束重要：使用不变量和示例；
- 数据对象较多：使用数据表；
- 存在状态分支：使用状态图或流程图；
- 有重要实现细节：展开说明。

**清晰度优先于格式统一。**

不得为了模板一致，把所有组件机械写成同样的“组件卡”；也不得为了保留细节，把所有辅助枚举都提升为核心类。

核心类通常包括：

- 模块入口类；
- 协调器；
- Port / Protocol；
- 关键领域对象；
- 关键 DTO；
- Adapter；
- 负责核心不变量的类。

辅助异常、枚举、简单 helper 和次要数据类可以在相关段落提及，或放入源码索引。

## 4.5 组件依赖和使用流程

本节负责把静态结构转换为真实运行过程，是模块 Wiki 的核心章节之一。

应区分：

### 静态依赖

回答：

- 谁依赖谁；
- 依赖的是抽象还是具体实现；
- 谁实现 Port；
- 谁负责装配；
- 哪些依赖方向必须保持。

### 动态调用

回答：

- 谁发起调用；
- 调用经过哪些组件；
- 关键状态或数据如何变化；
- 失败在哪一步收口；
- 结果如何回到上游；
- 哪个模块负责持久化。

一个复杂模块可以保留多张不同层次的图，例如：

- 模块总体调用链；
- 启动与注册流程；
- 一次请求主路径；
- 审批或恢复分支；
- 文件路径、网络调用等关键局部流程。

允许同一组件在多张图中出现，只要每张图回答的问题不同。

例如 `ToolExecutor` 可以分别出现在：

- 总体架构图：表示中心协调位置；
- Tool Call 时序图：表示动态行为；
- 审批分支图：表示与 Runtime 的边界；
- 文件路径流程：表示副作用前安全处理。

这种重复是有意义的，不应为了“去重”而删除。

每张图后必须给出文字结论，至少说明：

1. 发起者；
2. 协调者；
3. 依赖方向；
4. 关键状态或提交点；
5. 禁止的反向依赖或绕过路径。

## 4.6 对外接口与数据契约

本节只解释跨组件或跨模块稳定边界，包括：

- Public API；
- Port / Protocol；
- 关键 DTO；
- 关键数据对象；
- 配置契约；
- 生命周期；
- 关键不变量。

它不应重新完整介绍所有核心类，也不应变成第二份组件说明。

对于重要数据结构，应说明：

```text
谁创建
谁读取
谁修改
生命周期多长
是否持久化
必须满足哪些不变量
```

配置说明应明确：

- 配置项；
- 默认值；
- 消费者；
- 当前是否实际生效；
- 是否存在兼容字段或遗留字段。

如果某配置字段未被消费，必须明确标记为当前问题，不能仅照抄配置模型。

## 4.7 常见修改入口

本节帮助读者在理解架构后定位代码，不是文档核心主轴。

推荐使用任务导向表格：

| 修改目标 | 首要入口 | 可能涉及 | 必须保持的不变量 |
|---|---|---|---|
| 新增一种实现 | 对应组件的入口类或 Provider | Config、组合根、测试 | Port 契约和依赖方向不变 |

应覆盖真实、高频的开发任务，例如：

- 新增一个实现；
- 修改一类策略；
- 新增资源类型；
- 修改状态迁移；
- 增加 Provider；
- 调整持久化；
- 修改配置；
- 排查某类故障。

不需要把修改入口提前到每个组件，也不需要为每个类生成操作说明。

## 4.8 设计取舍、痛点和演进方向

本节必须严格区分四类内容：

### 当前设计

只写已经实现、可在代码中验证的事实。

### 设计取舍

解释为何采用当前方案。不能只写三行摘要，也不能只宣传收益。

一项完整取舍应尽量回答：

```text
原问题是什么
选择了什么方案
拒绝或未选择什么替代方案
为什么这样选择
带来了什么收益
付出了什么代价
当前边界是什么
```

不是每项都必须机械写满七个小标题，但必须提供足够信息，使读者真正理解判断过程。

### 已知痛点

必须是当前代码中真实存在、可以定位的问题，包括：

- 行为与契约不一致；
- 某个字段没有贯通；
- 错误语义被压缩；
- 恢复或幂等边界不足；
- 配置未消费；
- 文档与代码不一致；
- 当前方案的明确限制。

痛点不能写成泛泛的“性能有待优化”“可扩展性需要提升”。

### 演进方向

只写候选方案，并明确：

- 尚未实现；
- 尚未最终决定；
- 解决哪个痛点；
- 可能影响哪些模块；
- 存在哪些代价或前置条件。

禁止把演进方向写成现状，也禁止在当前设计中混入未来计划。

## 4.9 源码索引

源码索引是最后一层物理映射。

推荐内容：

- 目录树；
- 文件到逻辑组件的映射；
- 每个文件一句话说明；
- 必要的跨目录文件。

源码索引不应：

- 重新解释设计；
- 再写一遍类职责；
- 取代组件地图；
- 只列模块主目录而遗漏关键跨目录 Adapter、组合根或配置入口。

## 5. 组件划分原则

### 5.1 组件不是目录

一个组件可以跨越多个文件和子目录；一个目录也可以包含多个逻辑组件。

例如 Runtime Adapter 物理位于 `runtime/adapters/`，但 Tool 文档必须说明它是 Tool 与 Runtime 的接入边界。

### 5.2 组件数量没有硬限制

4～8 个只能作为阅读性参考，不是约束。

应拆出组件的条件：

- 具有独立、稳定职责；
- 有自己的核心类或协议；
- 有明确上游、下游或生命周期；
- 修改原因与其他部分不同；
- 对理解模块整体非常重要。

可以作为子组件或辅助机制的条件：

- 不具有独立对外职责；
- 主要服务某个核心组件；
- 但如果省略会造成架构理解缺口。

### 5.3 不为简洁牺牲完整性

以下内容即使不是独立公共组件，也通常应保留：

- Runtime Adapter；
- Bootstrap 装配；
- 外部 Provider；
- 观测和审计；
- 安全策略；
- 缓存、快照和恢复；
- 关键兼容层；
- 重要旁路机制。

正确做法是说明其层级和归属，不是删除。

## 6. 表达方式与细节深度

### 6.1 自顶向下，但允许读者选择深度

文档应形成自然的渐进层次：

```text
开头：快速建立整体认知
中部：理解组件和类
后部：理解流程、契约、设计和细节
结尾：定位修改入口和源码
```

细节放在后面，读者可以选择是否继续阅读。不能因为部分读者只看前几节，就删除对深入开发者有价值的实现细节。

### 6.2 表格、段落和图按内容选择

不要求所有组件使用统一形式。

- 表格适合比较稳定职责；
- 连续段落适合解释设计和复杂逻辑；
- Mermaid 适合表示关系、流程和状态；
- 代码块适合表达层次、调用链和不变量；
- 列表适合职责、边界和限制。

目标是“表达清楚”，而不是“格式看起来统一”。

### 6.3 详细说明必须产生认知价值

允许展开：

- 为什么存在某个中间层；
- 某个参数如何影响安全决策；
- 状态如何恢复；
- 数据何时持久化；
- 某个 Adapter 如何保持依赖倒置；
- 某个 Provider 为什么限制主机和路由。

不应展开：

- 每个简单 getter；
- 每个枚举值的机械翻译；
- 与模块目标无关的实现噪声；
- 仅复述代码语句但没有抽象结论的内容。

## 7. 重复与交叉引用规范

### 7.1 允许的重复

同一对象可以在不同抽象层出现：

| 出现位置 | 侧重点 |
|---|---|
| 模块位置图 | 它在系统中的角色 |
| 组件图 | 它在模块中的结构关系 |
| 类职责说明 | 它负责什么、不负责什么 |
| 动态流程 | 它运行时如何行为 |
| 设计取舍 | 为什么采用它 |
| 痛点章节 | 当前有什么问题 |

只要侧重点不同，就不是无意义重复。

### 7.2 应删除的重复

应删除：

- 原文复制；
- 两张图表达完全相同的关系；
- 同一事实在不同章节给出不同结论；
- 只改变措辞、不增加视角的重复；
- 旧版本、阶段编号和已经失效的历史说明；
- 同一类的完整职责表在多个章节重复维护。

### 7.3 跨模块说明规则

模块文档应自包含到足以理解本模块，但完整机制仍要有主归属。

推荐表达：

```text
先解释当前模块参与了什么
→ 给出足够完整的局部流程
→ 明确边界由谁负责
→ 链接到主归属文档查看完整细节
```

禁止：

```text
本模块与 Runtime 有关，详见 Runtime
```

这种写法没有提供任何当前模块视角的信息。

## 8. 图表规范

### 8.1 必需图

复杂模块原则上至少包含：

1. 模块位置图；
2. 组件关系图。

关键流程图按需要增加，不设硬数量上限。

### 8.2 不同图回答不同问题

| 图 | 回答的问题 |
|---|---|
| 模块位置图 | 模块为什么存在、上下游是谁 |
| 组件图 | 模块内部有哪些组成部分 |
| 依赖图 | 谁依赖抽象、谁实现、谁装配 |
| 时序图 | 一次调用按什么顺序发生 |
| 状态图 | 状态如何转换 |
| 局部流程图 | 安全、缓存、恢复等关键机制如何工作 |

### 8.3 图后必须有结论

图不能独立承担全部说明。每张图后至少说明：

- 发起者；
- 调用方向；
- 协调者；
- 关键数据或状态；
- 禁止的依赖或绕过方式。

### 8.4 禁止的图

禁止：

- 把完整源码目录直接画成组件图；
- 把所有类塞进一张全景图；
- 用三张图重复同一关系；
- 出现未解释的节点；
- 只画模块内部，导致模块与系统脱节；
- 图与实际代码调用方向不一致。

## 9. 事实、判断和计划的分离

所有 Wiki 内容必须能明确归入以下类别：

| 类别 | 含义 | 表达要求 |
|---|---|---|
| 当前实现 | 代码已存在且可验证 | 使用确定语气 |
| 设计取舍 | 已选择方案及原因 | 写清收益、代价和边界 |
| 已知痛点 | 当前真实缺陷或限制 | 指向具体代码或行为 |
| 演进方向 | 候选方案 | 明确尚未实现或未决定 |
| 历史背景 | 帮助理解的过去信息 | 只保留仍有认知价值的部分 |

禁止使用模糊阶段语言，例如：

- “阶段三已完成”；
- “v2 将支持”；
- “后续可能优化”；
- “按照总体设计第 X 节”。

除非项目仍正式使用该阶段计划作为当前规范。Wiki 应描述当前系统，而不是保存开发日志。

## 10. 编写流程

后续每个模块采用以下流程：

### 10.1 代码事实扫描

读取：

- 模块公共导出；
- 核心协调类；
- Port / Adapter；
- 组合根；
- 配置；
- 关键持久化；
- 相邻模块接入点；
- 现有文档。

扫描产物是内部结构卡，不需要长期与 Wiki 并行维护。

### 10.2 确认模块边界

先确定：

- 模块负责什么；
- 相邻模块负责什么；
- 哪些跨目录类型逻辑上属于本模块说明；
- 哪些机制需要完整说明；
- 哪些内容只做摘要并链接。

### 10.3 建立组件地图

先形成：

```text
模块
→ 核心组件
→ 能力实现
→ 外部接入
→ 辅助机制
```

再确认核心类，不按文件顺序直接写正文。

### 10.4 完成完整初稿

按照九节结构自顶向下完成，不在初稿阶段过度压缩。

### 10.5 事实核验

逐项核对：

- 类名和路径；
- 调用方向；
- Port 的定义和实现；
- 运行时真正消费的配置；
- 审批和恢复的权威事实；
- 快照与动态状态的区别；
- Journal 与恢复事实的区别；
- 当前代码与旧文档是否冲突。

### 10.6 局部优化

只处理：

- 无意义重复；
- 章节层级混乱；
- 事实冲突；
- 过时内容；
- 表达不清；
- 图和文字重复但无新增视角。

不得进行以下“优化”：

- 为控制行数强行压缩；
- 为统一格式把全部内容改成表格；
- 为突出修改入口改变整体结构；
- 为避免重复删除跨模块上下文；
- 为减少组件数量合并重要机制；
- 把详细设计压缩为口号。

## 11. 文档维护规则

文档更新由稳定知识变化触发，不要求每次代码修改都更新 Wiki。

### 必须更新模块 Wiki

当发生：

- 模块职责或边界变化；
- 新增、删除或重组逻辑组件；
- 核心类、Port 或 Adapter 职责变化；
- 关键流程、状态机、审批、恢复或持久化变化；
- 对外接口和数据契约变化；
- 设计取舍发生变化；
- 已知痛点被修复或出现新的重要痛点。

### 必须更新 Wiki 首页

当发生：

- 全局模块地图变化；
- 请求主链变化；
- 模块依赖方向变化；
- 新增第一类模块；
- 推荐阅读路径或全局边界变化。

### 可能需要更新 README

只有当变化影响：

- 项目定位；
- 总体分层；
- 对外展示的工程亮点；
- 当前能力和边界；
- 快速启动方式。

### 通常无需更新

- 私有 helper 的内部重构；
- 不改变职责的文件移动；
- 小型异常和枚举调整；
- 局部实现优化且不影响开发者理解。

## 12. 反模式与历史教训

### 12.1 把 Wiki 写成修改手册

错误表现：

- 开头就是“修改某功能去哪个文件”；
- 组件说明围绕开发任务组织；
- 架构位置和依赖关系被弱化。

后果：读者能改局部代码，但无法判断修改是否破坏整体边界。

### 12.2 为了简洁缩小组件范围

错误表现：

- 把 Runtime Adapter、Bootstrap、Provider、观测等重要部分删除；
- 强行控制组件数量；
- 模块被写成孤立子系统。

后果：失去总体性，不符合自顶向下理解要求。

### 12.3 强制所有组件套统一卡片

错误表现：

- 所有组件使用相同表格；
- 复杂流程被压成一句话；
- 设计细节无法展开；
- 文档看似整齐但认知价值降低。

正确原则：结构统一到章节层级，表达形式由内容决定。

### 12.4 机械去重

错误表现：

- 因为 `ToolExecutor` 已在组件图出现，就从流程图删除；
- 因为审批主归属 Runtime，Tool 文档只留一句链接；
- 因为设计章节会再解释，就删掉组件章节中的必要说明。

正确原则：删除无新增视角的重复，保留不同抽象层的解释。

### 12.5 过度压缩设计取舍

错误表现：

```text
选择了 X
因为解耦
代价是复杂
```

这种说明不足以帮助读者理解架构判断。

应补充原问题、替代方案、选择原因、收益、代价和边界。

### 12.6 把物理目录当逻辑架构

错误表现：

```text
模块
→ 目录
→ 文件
→ 类
```

正确顺序：

```text
模块
→ 逻辑组件
→ 核心类
→ 协作流程
→ 源码文件
```

### 12.7 把计划写成现状

错误表现：

- 候选接口使用确定语气；
- 未实现功能写入“当前能力”；
- 旧阶段计划仍作为主说明。

正确做法是严格分离当前设计、痛点和演进方向。

## 13. 验收准则

完成一篇模块 Wiki 后，应分别进行“快速阅读验收”和“深入阅读验收”。

### 13.1 快速阅读验收

只阅读前 3 节，应能回答：

- 模块为什么存在；
- 模块的直接上下游是谁；
- 它在一次系统请求中的位置；
- 模块有哪些核心组件；
- 哪些是核心组件、能力实现、外部接入和辅助机制。

### 13.2 深入阅读验收

阅读全文，应能回答：

- 每个组件有哪些核心类和协议；
- 每个核心类负责什么、不负责什么；
- 谁调用谁；
- 静态依赖和动态调用有何区别；
- 数据由谁创建、读取、修改和持久化；
- 字段是权威事实、引用、派生值还是缓存；
- 名称相近的数据对象是否已解释生命周期和边界；
- 关键失败如何收口；
- 设计为何这样选择；
- 当前有哪些真实问题；
- 候选演进会影响哪些部分；
- 修改某项功能应从哪里开始；
- 具体源码在哪里。

### 13.3 一致性验收

检查以下内容：

- 首页、README 和模块 Wiki 术语一致；
- 类名和文件路径与代码一致；
- 同一机制只有一个完整主归属；
- 其他文档的摘要不与主归属冲突；
- 当前实现和未来计划没有混写；
- 图中的调用方向与代码一致；
- 配置项确实被当前代码消费；
- 没有过时阶段编号和旧 Runtime 术语。

### 13.4 内容完整性验收

必须确认没有因为压缩而遗漏：

- 相邻模块上下文；
- Port / Adapter；
- 组合根；
- 配置；
- 关键持久化；
- 关键支持机制；
- 安全与失败边界；
- 真实痛点；
- 源码跨目录入口。

## 14. 最终判断原则

当“更短、更统一”和“更完整、更清楚”发生冲突时，优先后者。

后续 Wiki 的共同标准是：

> 以自顶向下的完整代码认知为第一目标；保留模块与系统的总体关系、重要组件和支持机制；允许同一对象在不同抽象层被有侧重地解释；根据内容选择表格、段落和图；详细说明设计的原因、代价和边界；修改入口和源码索引放在理解架构之后。

任何后续优化都必须回答：

```text
是否仍能完整理解模块在系统中的位置？
是否仍能看见所有重要组件和接入边界？
是否仍能从组件进入核心类和细节？
是否仍能理解谁调用谁以及为何这样设计？
```

只要其中任一答案变差，该优化就不应采用。
