“责任包”是可交给开发人员的工作边界，不要求多人并行。多个阶段会修改引擎，同一文件必须按上述顺序衔接，不允许分别实现两套工具循环。

公共约束：本地文件存储、单宿主进程写入、每运行一个驱动、工具串行、Session 租约先于运行短锁；工具和模型调用不能持运行短锁。外部副作用不是本地事务的一部分。现有 API 路由不增加强制重放入口。所有新增代码注释使用中文。

阶段依赖固定：C03 一次定义完整 schema（含副作用、预算、执行证据和错误分类），C04/C05 实现完整序列化与控制提交原语，C06 接入所有新格式读取分支，C07/C08 补强审批取消竞争，C10a 才启用安全恢复重试并增加作者侧配置。不能先发布不完整 schema 再用同一版本改变含义。C06 需要的保守工具契约、审批状态读写和执行证据归一化必须在 C06 可调用，不得引用到 C10a 才存在的方法。所有中间 commit 只供开发审查，不单独上线。

### 0.1 完成后的唯一链路

```text
助手消息落盘
  → 冻结本批调用账本
  → 按 ordinal 选择调用
      → 普通工具：审批校验 → 记录 STARTED → 监管执行 → 保存结果 → 补投影
      → 委派工具：稳定准备 → 保存关联 → 启动/等待子运行 → 保存子结果 → 补投影
  → 本批剩余调用
  → 批次完成迁移只发生一次
  → 下一次模型调用

任意入口恢复：取得唯一驱动权 → 补投影 → 处理终态/取消 → 核验事实
  → 复用 / 执行 / 安全重试 / 等审批 / 续子运行 / 停止
```

### 0.2 跨阶段统一命名

以下现有类型在全文按此职责引用：`RuntimeEngine`（运行引擎）、`CancellationService`（取消及能力任务控制服务）、`SessionRunCoordinator`（会话运行协调器）、`ToolExecutorAdapter`（工具端口适配器）、`ToolExecutor`（安全工具执行器）、`RunRepository`（运行仓储协议）、`ApprovalService`（审批服务）。新类型字段以总设计第 4 节为基线，本文明确列出的补充字段必须同步实现，不能仅照旧模型表漏掉它们。

### 1.1 C01：执行端和取消扫描

**文件、类、方法及必须执行的修改**

| 文件/所有者 | 方法 | 具体改动 |
|---|---|---|
| `runtime/application/engine.py`，运行引擎 | `_execute_tools_action` | 收到工具端口结果后，先判断 APPROVAL_REQUIRED，再进入 sequence 增加、统计、消息构造及完成事件分支；审批分支直接调用 `_suspend_action` |
| 同上 | `_suspend_action` | 入参新增 `source_message_id: str`，WAITING_APPROVAL 引用原助手消息；禁止再使用 `messages[-1]` 假设最后消息为本次工具结果 |
| 同上 | `_tool_completed_event` | 入口拒绝 APPROVAL_REQUIRED；允许 completed/failed/cancelled，保留现有失败无消息的读取兼容 |
| 同上 | `_tool_started_event`、`_suspend_action`、`resolve_approval` | 新事件写 `tool_event_semantics=2`；此字段仅表示语义版本，不等同于后续账本 schema_version |
| `runtime/adapters/tool_executor_adapter.py`，工具端口适配器 | `execute` | 审批条件改为 `requires_approval and not invocation.approved`，每次均返回审批需求；删除 `_waiting_calls` 及相关清理，暂保留 `_executed_calls` 防重入直至 C06 替换 |
| `runtime/domain/events.py` | 新纯函数 `is_terminal_tool_event(event: RunEvent) -> bool` | 只识别 TOOL_COMPLETED 且 status 在 completed/failed/cancelled；approval_required 为 false；未知值抛格式错误，不能默认为成功 |
| `runtime/application/engine.py` | 新 `_scan_legacy_tool_activity(events)` | 统一解释旧/语义2工具事件，供两个取消入口复用，算法见下 |
| 同上 | `recover_cancellations`、`complete_cancellation` | 替换各自 open_tools 扫描，使用统一扫描结果；等待审批不能被误判为孤儿执行资源 |

`RunEvent`（运行审计事件）沿用现有类型。新增 `ToolActivityScan`（历史工具活动扫描结果）位于 `runtime/application/dto.py`，只在内存保存：`active: dict[str, RunEvent]`、`waiting: dict[str, RunEvent]`、`terminal_call_ids: frozenset[str]`。它是旧事件解释器结果，不是第二份持久账本。

扫描按 sequence 严格递增处理：

1. TOOL_STARTED：从 waiting 移除该 call_id，写入 active；这表示进入一次执行链路，未证明副作用发生。
2. WAITING_APPROVAL：从 active 移除，写入 waiting；旧 TOOL_COMPLETED/approval_required 等效处理，不进入 terminal。
3. APPROVAL_RESOLVED：从 waiting 移除；通过时不自行放入 active，只有后续 TOOL_STARTED 才能表示新尝试；拒绝时由取消收尾结束调用。
4. 真终态：同时移除 active/waiting，加入 terminal；不得把后续审批事件覆盖真实成功终态。
5. 取消补写：对 active 与尚未终态的 waiting 补 cancelled 审计；waiting 的 effect_certainty 为 known，active 为 unknown。资源遗留判断只检查 active，并结合已有资源记录，不能把 waiting 计为待清理能力任务。

C01 暂不改变开始事件产生时机；审批前仍可能有开始事件，语义是“尝试进入调用链”。C06 才将普通审批预检前置。禁止在 C01 顺便把开始事件当“处理函数已执行”的证明。

**本次调用链**：端口返回审批需求 → 不增 message_sequence → 创建审批记录 → 保存挂起检查点/运行 → WAITING_APPROVAL；批准后 → 再进入工具链 → 一条真实结果 → 一条完成事件。

**验收**：扩展 `test_runtime_engine.py`、`test_tool_executor_adapter.py`、`test_session_cancel.py`、`test_cancellation_persistence.py`。断言审批不增结果消息数；连续两次未批准调用执行器次数为零；批准结果关联正确 call_id；等待审批取消不产生孤儿清理阻塞；历史假终态不能被当成功。

负责领域类型和序列化，不写真实外部调用。新增 `common/tool_replay.py`、`runtime/domain/tool_recovery.py`；修改 facts.py、dto.py、ports.py、tools/base.py。

### 2.2 状态迁移表（开发不得自行新增边）

| 原状态 | 允许目标 | 触发者及约束 |
|---|---|---|
| PENDING | STARTED / WAITING_APPROVAL / WAITING_CHILD / CANCELLED | 正常执行/审批预检/委派关联/已受理取消 |
| STARTED | SUCCEEDED / FAILED / WAITING_APPROVAL / WAITING_CHILD / UNCERTAIN / CANCELLED | 真实返回/动态审批/委派关联/不明效果/取消；WAITING_CHILD 仅委派路径 |
| STARTED | STARTED | 仅恢复 RETRY，attempt 与 retry_count 各加1，先持久化再执行 |
| WAITING_APPROVAL | STARTED / CANCELLED | decision=true 后执行，拒绝/取消不执行；仍无决议保持原状态 |
| WAITING_CHILD | SUCCEEDED / CANCELLED | 子终态可读取后回填；父取消按父子取消协议处理 |
| SUCCEEDED / FAILED / CANCELLED | 原状态 | 仅完全相同事实幂等重入，不生成新事件或新消息 |
| UNCERTAIN | 原状态 / CANCELLED | 自动执行禁止；运行失败收口，或先前受理的取消收口但保留 uncertainty_reason |

未知结果的安全重试由 STARTED→STARTED 完成，不先写 UNCERTAIN 再偷偷回到 STARTED。等待审批没有结果快照；普通成功/失败必须有快照；失败快照必须有 error；只有取消允许 message_id=None。

### 2.3 冻结调用参数类型

`ToolRecoveryService`（工具恢复服务）的签名中：run 使用 AgentRun；checkpoint 使用 RunCheckpoint；call_id/approval_id/child_run_id 使用 str；source_message 使用 RunMessage；contracts 使用 `Mapping[str, ToolRecoveryContract]`；outcome 使用 ToolOutcomeSnapshot。这些不是开发人员自选的 dict。

批次 ID 固定为原助手消息 ID，identity 固定为 `(run_id, call_id)`，无第二套 operation ID。UUIDv5 输入统一通过 `json.dumps(parts, ensure_ascii=False, separators=(",", ":"))` 编码。KEYED 键不含 attempt。

**验收**：新增 `tests/runtime_v2/test_tool_recovery_models.py`；覆盖每一条合法迁移和至少每种被拒绝迁移、序列化往返、未知版本、重复调用身份、终态缺结果。此时不接入引擎，现有运行行为不改变。

## 3. 阶段三：实现可补写的持久提交（C04、C05）

### 3.1 C04：仓储必须提供的原语

文件适配器 `RunRepositoryAdapter`（文件运行仓储）与 `InMemoryRunRepository`（内存运行仓储）实现相同测试契约，接口定义在运行仓储协议。

| 方法 | 按序执行的内部步骤 | 失败返回规则 |
|---|---|---|
| `load_tool_ledger(session_id, run_id)` | 校验路径 → 不存在返回 None → 解析版本和字段 → 校验容器/调用/意图身份 | 损坏抛 ValueError；不得返回空账本 |
| `save_tool_ledger(ledger, expected_revision)` | 重读当前版本 → 校验 expected → 确认目标 revision=expected+1 → 原子替换 | 版本不匹配抛 ValueError，不覆盖 |
| `ensure_tool_messages(session_id, run_id, messages)` | 加载当前消息 → 按 ID 对比完整内容 → 缺失项要求序号连续后追加 → 原子保存 | 同 ID 异内容、同序号异 ID、跳号均拒绝 |
| `ensure_tool_events(session_id, events)` | 严格加载连续前缀 → 同序号全内容相同跳过 → 连续追加缺失项到内存 → 原子替换完整 JSONL | 序号冲突/缺口拒绝；不复用逐行 append，以免写到半行后无法补写 |
| 新 `ensure_tool_run(base_run, target_run)` | 当前等于 target 则成功；等于 base 才保存 target；其他情况冲突 | 禁止旧投影覆盖取消/成功终态 |
| 检查点仓储新 `ensure_tool_checkpoint(base, target)` | base/target 均可 None；当前等于 target 幂等成功；等于 base 才写 target 或删除（target=None） | 不覆盖更先进检查点，不无条件删除 |

因此 C03 的投影意图还必须包含 `base_checkpoint: RunCheckpoint | None`；两份 base 快照只在未完成意图中临时保存，清意图即释放。内存仓储也要实现比较条件，不允许测试替身无条件成功。

新增 `_file_support.write_text_atomic(path, text)`：与已有 JSON 原子写相同的临时文件、flush/fsync、同目录 replace 协议，供完整 JSONL 投影使用。旧日志已损坏不自动截尾；新协议保证工具事件写入只见旧完整文件或新完整文件。普通 LLM 事件的旧 append 崩溃窗口属于既有路径，损坏时明确阻断，不宣称本次覆盖所有历史事件写入。测试包含替换前硬退出，而非仅在写入方法返回后注入错误。

`ApprovalRepository`（审批仓储协议）新增 `ensure(record)`：相同未决幂等；同身份未决→已决允许；相同决议幂等；相反决议、身份改变、已决→未决拒绝。旧 consumed 无 decision 不能由 ensure 升级为批准。取消消费无决定时保持 decision=None，不代表批准。

**验收**：新增 `test_tool_ledger_repository.py`，同一参数化契约覆盖文件/内存两实现；不存在、损坏、版本冲突、幂等重复、目标漂移全部覆盖。C04 不允许引擎开始写账本。

### 3.2 C05：投影服务，不接外部工具

新文件 `runtime/application/tool_recovery.py` 实现恢复服务。构造为 `__init__(runs: RunRepository, checkpoints: CheckpointRepository, approvals: ApprovalService)`；CheckpointRepository（检查点仓储协议）使用现有类型。

内部方法固定如下：

- `_build_projection(base_run, target_run, base_checkpoint, target_checkpoint, messages, events, approval, revision) -> ToolProjectionIntent`：校验调用身份及序号，所有时间戳/消息 ID 在这里一次生成；不执行 I/O。
- `_commit_projection(ledger, intent, expected_revision) -> ToolCallLedger`：先保存带意图账本，再调用 `_apply_projection`；返回清意图后的账本。
- `_apply_projection(ledger: ToolCallLedger) -> ToolCallLedger`：按下面固定顺序补写，不自行创建新的业务事实。
- `recover_projection(session_id: str, run_id: str) -> None`：无账本/无意图直接返回；有意图调用 `_apply_projection`。

固定补写顺序：

```text
① 带结果/控制决定的账本和 intent 原子保存
② 如果有 approval：ApprovalService.ensure_projection(record)
③ ensure_tool_messages
④ ensure_tool_events
⑤ ensure_tool_checkpoint(base_checkpoint, checkpoint)
⑥ ensure_tool_run(base_run, run)
⑦ 保存 revision+1 的账本，pending_projection=None
```

任一步失败立即停止，不清 intent，不发送完成通知，不推进下一调用。恢复使用意图内原对象，不重新分配序号/时间。投影期间所有本运行写入均在调用方持有的同一个运行短锁内；本服务不重入获取锁。

新增 `ApprovalService.ensure_projection(record) -> None` 只委托仓储 ensure，不作审批决定。批次完成也必须生成同类意图，不能在工具结果都写完后再用裸的 checkpoint/save_run 双写重开崩溃窗口。

终态提交闭环：新增 `ToolRecoveryService.commit_run_failure(run, error, checkpoint) -> ToolCallLedger`，由引擎的失败策略调用，构造 RUN_FAILED、失败运行目标及 checkpoint=None，走同一意图协议；不重复写工具结果。`block_uncertain` 复用该构造逻辑但同时记录 UNCERTAIN。普通工具已 FAILED、运行还未失败时崩溃，恢复必须先完成失败策略，禁止因为该调用已从 pending 移除就执行后一项。终态意图必须在任何“已结束直接返回”之前补齐，否则检查点删除、RUN_FAILED 及清意图会遗漏。

所有工具提交方法必须在短锁内重新读磁盘 run/checkpoint 作为 base，不能把已在内存修改统计值的 run 当 base；target 才应用本次变更。new intent 生成前补齐已有 intent，锁外不分配新事件序号。审核 `_event`、失败/放弃/取消/成功入口：它们若要写同运行事实，必须先排空工具投影，不能越过 intent 提交终态。取消请求本身可单独写 cancellation.json 并发信号，不等待投影后才受理。

**验收**：`test_tool_projection_recovery.py` 在①之后和②—⑦每步前后注入失败，重新实例化仓储/服务后补写两次，目标文件内容一致，外部执行器调用数始终为零。损坏/冲突时保留意图供诊断，不删除意图强行通过。

## 4. 阶段四：普通工具执行与恢复接入（C06）

### 4.1 文件和所有权

修改 engine.py、execution.py、ports.py、dto.py、tool_executor_adapter.py、bootstrap/runtime_factory.py 及 Eval 装配/工具替身。该阶段拥有唯一普通工具执行循环，不增加独立 scheduler。

`RunExecution`（内存运行现场）新增 `tool_batch_id: str | None = None`；恢复时来源于检查点。不得将账本复制成第二份可变状态缓存，每次持久写前重读账本。引擎构造新增必传 `tool_recovery: ToolRecoveryService`，生产与测试装配同时更新，不保留可绕过账本的默认 None 分支。

### 4.2 服务方法和处理顺序

| 方法 | 开发执行步骤 |
|---|---|
| `plan_batch(run, source_message, contracts, checkpoint)` | 校验助手消息存在、调用顺序及唯一 ID → 同批已计划则完整比对并返回 → 为每项建 PENDING → 构造 EXECUTE_TOOLS 检查点，pending 为所有 call_id → 通过 C05 提交 |
| `begin_attempt(run, call_id, checkpoint)` | 重读账本/取消事实 → 允许 PENDING 或已批准 WAITING_APPROVAL；此阶段 STARTED 不重试 → attempt+1 → 构造 TOOL_STARTED → 提交并返回记录 |
| `commit_outcome(run, call_id, outcome, checkpoint)` | 校验对应 STARTED、结果身份 → 写终态及稳定结果消息 → pending 排除该终态调用 → 统计只增加一次 → C05 提交 |
| 新 `complete_batch(run, batch_id, checkpoint)` | 校验该批所有调用 SUCCEEDED（委派子业务失败可已取得结果）→ 纯状态迁移 ToolBatchCompleted → 生成 INVOKE_LLM 目标检查点与运行 → C05 提交；已完成批次重入直接复用 |
| `block_uncertain(run, call_id, reason, checkpoint)` | 记录 UNCERTAIN、诊断事件；同一投影包含失败运行目标，运行 error=TOOL_OUTCOME_UNCERTAIN；无工具成功消息；不再先写未知状态后依赖单独 `_fail` 才收口 |

`ToolBatchCompleted`（工具批次完成领域事件）仍用现有类型，携带结果消息 ID，按原 ordinal 排序。

### 4.3 引擎方法级实现

1. `_execute_tools_action` 先从 `source_message_id` 定位助手消息，调用 plan_batch；恢复已有账本时不重新生成调用。
2. 新 `_resume_tool_batch(execution, run, plan, output_port) -> RunResult | None` 只分派恢复决策；普通调用由新 `_execute_one_tool(execution, run, record) -> ToolStepResult`（单工具步骤结果）执行。该内存类型定义于 dto.py，字段 `kind: completed|suspended|blocked|cancel_pending`、`outcome: ToolOutcomeSnapshot | None`、`run_result: RunResult | None`；completed 必须有 outcome，其他分支必须有 run_result。suspended 包括等待审批及 control_status=recoverable，blocked 表示明确阻断，cancel_pending 表示取消清理中，避免一个 None 同时丢失审批/失败/取消信息。
3. `_execute_one_tool`：短锁内重读取消 → 审批预检 → 有审批需求调用 C05 已实现的 wait_approval → begin_attempt → 释放锁 → run_operation 调工具 → 得到结果后在短锁内 commit_outcome → 返回。C06 同时将 `_calls_from_checkpoint` 的调用方改为“新格式查账本/旧格式读 tool_calls”；不能将新检查点交给旧切片读取器。审批最小账本决议读写随 C06 接入，C07 负责完整决议冲突/崩溃验收，不保留一个写新格式却只能用旧审批恢复的中间接口。
4. try 范围只包外部执行，不包 commit_outcome；持久化错误统一向入口转 PERSISTENCE_FAILURE，禁止追加一条业务 FAILED 覆盖原结果。
5. `_execute_tools_action` 对完成结果继续下一 ordinal；失败停止；全部完成调用 complete_batch，更新 execution.state/action/message_cursor；不得另行 `_persist_running_transition` 重写该次投影。
6. `_tool_started_event/_tool_completed_event` 不再由新普通工具路径直接写入，事件对象交服务一起提交；C01 旧数据解释代码保留。
7. 删除 `_executed_calls`，`clear_run` 如已无缓存可保留协议空实现或删除调用，固定选择：保留无状态空实现以兼容现有 clear_run 调用，不增加新缓存。

8. 新 `_reload_tool_execution(execution, run_id)` 在每次投影完成后重读 run/messages/checkpoint：同步 execution.state/action/budget、replace_run_messages，并替换驱动局部 messages/sequence/event_number；防止下次 `_save_messages` 用旧列表覆盖工具结果。不能只更新磁盘或 message_cursor。
9. 新检查点字段 `replay_context: bool | None = None`：真正 LLM 请求前的检查点置 true；complete_batch 生成的下一轮准备点置 false；旧值 None 按原协议处理。工具批次进入下一轮 LLM 时清 execution.replay_active_context，重建包含工具结果的上下文；重启若检查点为 false 同样重建。仅重试同一次已冻结的模型请求才重放旧 Context Version。对应修改 `_llm_checkpoint`、`_persist_running_transition` 与 `context/provider.py` 的恢复测试。

实际授权检查不得依赖粗预检：新增 `ToolExecutor.execute_for_runtime(name, arguments, context, *, approved: bool) -> ToolResult`（底层工具结果），复用 `_run_chain` 的参数校验→能力解析→当前策略。底层结果新增 `approval_required: bool=False`，仅策略 ASK/声明需审批且 approved=false 时返回 true、execution_evidence=NOT_STARTED，不调用交互 Channel 或 Handler。适配器转换成运行时 APPROVAL_REQUIRED。DENY 总是拒绝；approved 只绕过对应 ASK，不能由预检“无需审批”推导为 true。原 execute_approved 只留给明确已批准的旧调用方，新 Runtime 不再无条件调用它。此安全链适配及证据归一化随 C06 实现，C10a 只扩展重试资格，不重复改执行链。

**为后续错误回灌保留的边界（已确认后续方向）**：`commit_outcome` 对普通 FAILED 只保存调用失败及结构化错误，不结束整个 Run。引擎新增 `_after_tool_failure(execution, run, record) -> RunResult` 集中执行当前停止策略；以后改为回灌模型只调整此应用层分支及批次收口，不改账本事实。错误记录至少保留原 tool error_code、output、execution_evidence、call_id，不能在适配器统一成 TOOL_FAILURE 后丢掉原错误分类。UNCERTAIN、持久化损坏、取消与资源未收尾不能伪装成普通可修正错误交模型自由重试。模型换参数属于新的 call_id，不能覆盖原调用冻结参数。

具体字段补充：底层工具结果已有 error_code/error_type，运行时结果与结果快照分别新增 `tool_error_code: str | None`、`tool_error_type: str | None`，与运行控制错误分开保存；output 使用现有错误正文，不另造一份 error_message。调用链固定为“取得结构化结果 → commit_outcome 保存调用事实及错误消息 → _after_tool_failure 决定运行停止”。_after_tool_failure 不写第二条工具结果。后续阶段将修改此分支返回值、允许批次失败项参与收口并回灌模型，不能声称只改一行策略就能完成。中文 TODO 留在此方法说明后续任务及对应测试，但本轮必须已经实现上述职责拆分。

本次 `_after_tool_failure` 调用 commit_run_failure，禁止直接沿用 `_fail_locked` 的 run→删checkpoint→event 三步裸写。未执行的后续 PENDING 记录保留且禁止再调度；运行终态优先于调用 pending，不能通过手工 resume 重开终态。

### 4.4 恢复入口的明确算法

`resume_run` 在既有 Session 租约内，短锁先检查 has_driver；无驱动时新增 `reserve_driver(run_id) -> None` 预留运行控制权。**reserve_driver/bind_driver 及原 register_driver 的衔接必须在 C06 同时实现**，其接口规则见阶段五，不能等到 C08 才补被调用方法。预留失败不允许更新 run 或事件。然后：

```text
recover_projection
→ 若成功/取消提交未完成，先走既有提交恢复，不能启动业务
→ 重读 run；所有提交意图已补齐后，若终态才返回真实终态
→ 若取消请求存在，释放本次预留后交取消收尾
→ reconcile
→ 验证 Context Version、源消息、检查点所指批次
→ 实际 events/messages 校验连续后取下一序号
→ 绑定重建的 execution/token，写 RUN_RESUMED
→ 按 decisions 驱动
→ finally 注销
```

`reconcile` 不接受检查点 pending 为唯一事实：先读账本完整批次，验证记录与源助手消息一致，再依据结果快照、审批/子运行关联计算动作。此阶段所有 STARTED 无结果先 BLOCK；C10 才放开白名单安全重试。文件不存在但检查点声明新账本版本时是损坏，不转旧格式。

最终批次完成由 C05 意图保护，因此迭代次数只加一次。空 pending 只有“已规划批次且所有结果齐全”才完成；没有批次身份的空列表仍报 INVALID_STATE。

批次入口范围明确：plan_batch 的意图已保存后，恢复必须优先它，即使 checkpoint 仍指 INVOKE_LLM；plan_batch 之前崩溃可能重新调用模型，该时刻尚未执行任何本批工具，属于本轮不处理的模型结果可靠提交窗口。不得为了补这个窗口重构全部模型提交。恢复时当前批次所有记录都参与判定，不能只读 pending_call_ids。

**验收**：A 成功结果保存后任一投影边界崩溃，恢复不再调用 A；B 尚未开始只执行一次；最后调用完成后恢复 iteration 只增一次；两个恢复入口只一个取得驱动；失败结果不自动重试；STARTED 未知结果不继续 B 或模型。

## 5. 阶段五：审批决定与取消提交闭环（C07、C08）

### 5.1 C07：审批恢复由账本决定

修改 approval_service.py、approval_repository.py、engine.py、session_run_coordinator.py。新增审批服务 `find(approval_id: str) -> ApprovalRecord | None`，可返回已消费记录；`get_approval_session_id` 改用 find，不能因 consumed 导致绕过 Session 锁。

`wait_approval(run, call_id, approval_id, checkpoint)` 固定：读取调用 → 计算稳定审批 ID（复用现有 `_approval_id` 算法）→ 构造待处理审批记录，call_id 绑定该调用 → 状态改 WAITING_APPROVAL → 纯状态机 ToolApprovalRequired → 构造 WAITING_APPROVAL（引用源助手消息、包含 call_id）→ 用 C05 同一次提交保存全部目标。重复挂起不追加第二条等待事件。

`decide_approval(run, approval_id, approved, checkpoint)` 固定：

1. 按账本查到且仅查到一个关联调用，校验运行与冻结参数。
2. 若账本已有相同 decision，先补意图后返回当前状态，不再消费/发事件；反向决定拒绝。
3. 未决时必须处于 WAITING_APPROVAL；保存 decision 与 consumed 审批目标；APPROVAL_RESOLVED 数据同时含 approval_id、call_id、approved。
4. true：运行目标通过 ApprovalGranted（批准领域事件）返回工具阶段，调用仍 WAITING_APPROVAL/decision=true，直至 begin_attempt 原子改 STARTED；false：先仅持久保存拒绝决定/APPROVAL_RESOLVED，运行保持挂起且调用不可执行，清意图后由引擎发起既有取消请求并走 complete_cancellation。恢复看到 decision=false 而尚无取消记录时必须补发取消请求，不能执行工具。拒绝不再独立直接写取消终态，避免绕过资源清理。
5. 全部经 C05 提交后才允许执行；禁止再调用旧 consume 先行删除决议机会。调用状态为 WAITING_APPROVAL 但 decision=true 时，reconcile 返回 EXECUTE 而非 WAIT_APPROVAL，避免批准后重启永久挂起。

`resolve_approval` 用 find + 账本核验 + decide_approval 替代原 consume；重启后相同批准请求只能恢复未执行项或复用结果，不能重复启动。运行已结束时相同决议返回终态，相反决议仍报冲突。旧 consumed 无 decision 分支留给 C11 证据判定，默认拒绝执行。

**验收**：审批 intent 保存前/后、consumed 保存后、批准检查点后、实际执行前后分别崩溃；相同批准重入、批准拒绝竞争、取消与批准竞争。只允许先获得短锁并持久化的决定生效；已受理取消优先于启动新工具。

### 5.2 C08：驱动权、结果提交与取消收尾

修改 cancellation_service.py、engine.py、session_run_coordinator.py。不新增第二把运行锁，不将取消请求改为等待长操作。

取消服务的驱动登记接口已由 C06 引入；C08 按以下契约接入取消收尾，不重新定义一套：

- `reserve_driver(run_id: str) -> None`：调用方持 gate，检查 `_drivers` 后加入；不写 token、不创建任务。
- `bind_driver(run_id: str, token, request) -> None`：要求已 reserve，把 token/request 绑定到现有集合；不再次检查“重复驱动”。
- 原 `register_driver` 改为顺序调用 reserve+bind，供普通新运行入口使用；恢复入口使用分开的两步，解决“还没重建 execution 就必须占用恢复权”的时序。
- `unregister_driver` 同时清理预留和已绑定驱动；外部能力句柄及未清理证据不因此删除。

reserve/bind 拆分后保留原 `assert_resources_settled` 检查：无取消请求的业务恢复在 bind 前必须通过；已有残留能力或清理失败时只允许控制收尾，不启动工具。bind 必须重读持久取消记录并 signal，覆盖 reserve 与 bind 之间到达的取消。所有取得预留的路径使用 finally 释放，未取得预留的失败请求不得注销别人的驱动。

新增引擎 `_commit_observed_tool_result(...)` 私有方法：将已取得结果转快照后，使用现有 `_await_control` 保护完整的短锁提交。提交任务必须由当前驱动 await 到成功或明确存储错误；禁止 fire-and-forget。用户取消只取消能力任务，不取消这个持久提交任务。

`_finish_cancelled` 改为仅返回“当前状态+取消请求已受理”的结果，不在活驱动内递归完成取消；驱动 finally 释放登记与 Session 租约。协调器现有 `_drain_cancelled_run` 在租约释放后继续 complete_cancellation，沿用既有等待机制，不增加轮询线程。

不依赖用户从某个特定入口取消：审批拒绝、父取消、恢复发现已有取消请求时，均调用协调器已有去重收尾作业入口；直接使用引擎的测试/调用方则须在驱动注销后显式 complete_cancellation。shutdown 先等待受保护结果提交再注销，存储失败仍保留意图；进程硬退出无法保证内存中结果落盘，按 UNKNOWN 恢复，不声称消除这个窗口。

`complete_cancellation` 固定顺序：

1. 短锁内若 has_driver 为真，返回取消处理中，不写终态，也不等待自己。
2. recover_projection，重读真实 run 和取消记录；成功工具结果保留。
3. 锁外处理资源和子运行收尾；清理未确认仍阻塞。
4. 再进短锁，复查无驱动、无未清投影；账本未完成调用标取消，保存 `uncertainty_reason` 与 effect_certainty，等待审批不算残留资源。
5. 对账本取消记录先做工具投影（运行状态保持当前未结束状态），然后调用原取消提交协议写 RUN_CANCELLED/清检查点。两步骤中间崩溃，由持久取消请求继续收口；不得生成一个与工具意图同时存在的取消意图。
6. 删除重复 open_tools 补写的新格式路径；旧格式继续走 C01 扫描。

`recover_cancellations` 先补工具意图，再检查活动工具和资源；读取到 WAITING_APPROVAL 不得设置 orphaned_tool_cleanup_unverified。`confirm_cancellation_cleanup` 只确认资源清理，不能把未知业务效果改成成功。

**验收**：用屏障控制“工具返回→尚未提交”时到达取消，确认最终有真实成功工具结果与运行取消；写盘失败时不清意图、不提交假取消终态；活驱动内取消不死锁；重启无内存句柄时仍尊重历史未知资源证据。

返回与展示闭环（C06 定义字段，C08/C10a 使用）：`RunResult`（运行返回对象）新增 `control_status: Literal["cancelling", "recoverable"] | None = None`。只用于非终态响应，不改变持久运行状态机。`channel/web/app.py::_result_event` 对这两种值使用现有 run.suspended 事件，status 分别为 cancelling/recoverable，不能发 run.failed；前端 SSE 消费者映射 stopping/recoverable 并继续既有状态观察。最终失败/取消必须由真实终态产生。CLI 同步区分提示。补 SSE 合约测试，不能只测 activity 查询。

## 6. 阶段六：委派和混合批次（C09）

### 6.1 方法、字段与状态迁移

| 所有者/方法 | 明确改法 |
|---|---|
| 引擎 `_execute_tools_action` | 删除整批预扫描，消费到当前 ordinal 时才判断委派；此前普通工具必须提交完毕 |
| `PendingDelegation`（内存委派待办对象） | 保留 request/tool_call，新增 batch_id；删除用切片决定恢复的责任，tool_calls/tool_index 不再作为持久进度依据，调用方改查账本 |
| 引擎 `_handoff_target_action` | 先将本调用记 STARTED，再调用 prepare；attach_child 提交父关联与挂起后才 start；准备失败遵守“已创建子运行不得丢关联”的规则 |
| 恢复服务 `attach_child` | 校验子运行 parent/root/目标/输入与本调用一致；记录 WAITING_CHILD、child_run_id；pending_call_ids 保留本调用和后续调用；C05 提交 |
| `RuntimeDelegationAdapter`（委派适配器）`prepare` | 保留现有稳定子 ID 算法，不引入另一份子运行注册表；已存在 child 且输入不符直接拒绝 |
| 新委派端口 `async resume(child_run_id: str) -> None` | 委派适配器调用协调器恢复调度方法，具体状态分流见下；不在父短锁内等待子执行 |
| 引擎 `resume_delegation` | 先补父投影；若该父调用已 SUCCEEDED，返回/继续剩余批次，不再追加结果；否则读稳定子终态后 commit_outcome，message_kind=DELEGATION_RESULT，child_outcome 保留真实结局 |
| `state.py::_on_running/_on_suspended` | DelegationSubmitted 的 resume_stage 改 EXECUTING_TOOLS；DelegationCompleted 进入该阶段并返回 EXECUTE_TOOLS，iteration 不增；批次完成统一加一次 |

新增 `SessionRunCoordinator.schedule_resume(run_id: str) -> None`：复用已有 `_drivers` 任务表按 run_id 去重；创建调用 `resume_run` 的受管任务并沿用 `_driver_done`。不要在父流程直接 await 子完整运行，也不要重用只会 start_prepared 的调度分支。

父短锁只包本地 prepare+attach：沿既有父→子准备锁顺序，避免对已经持有父锁的路径再次调用会重入父锁的公开 prepare_run。不持父锁等待 child start/result/wait_terminal 或 child Session 租约；真正子业务调度在 attach 提交之后。父取消已受理时禁止继续 prepare/start，已创建但未启动子运行交原取消协议收口。prepare 抛错后若存在稳定子运行，优先核验/关联该子运行，不把它当可随意重试的普通失败。

适配器 `resume` 分流：已终态则不调度；Created（已创建未启动状态）调用现有 schedule_prepared；Running（运行状态）且无已登记任务则 schedule_resume；Suspended（挂起状态）无论等审批或等子运行都保持既有等待，由原控制入口唤醒，**不在本轮新增递归扫描/唤醒委派树**；存在取消请求则交取消收尾。适配器不自行创建 asyncio 业务任务。

父恢复若记录 STARTED 且 kind=delegation：调用同一 prepare 取得/复用子 ID再 attach，不用普通 NO_AUTO_RETRY 判定盲目停止；这依赖本地稳定准备协议，不能泛化到普通外部写工具。

### 6.2 固定调用链与退出条件

`A普通提交 → B开始 → prepare(B) → attach_child(B) → start/resume(B) → 父挂起 → B子终态 → commit_outcome(B) → C普通 → complete_batch → LLM`。

子运行 FAILED/CANCELLED/ABANDONED 都是“已取得委派结果”：父调用 SUCCEEDED、child_outcome 保留失败/取消等值，沿原产品语义交父模型处理。父自身取消时不得继续 C。

**验收**：扩展 `test_delegation_port.py`、`test_delegation_lifecycle.py` 与状态机测试；A/B/C、B/A、纯B、多次委派逐项通过。prepare后/关联前、关联后/start前、子完成/父结果前崩溃均只使用一个子 ID；重复回调只有一条父结果；iteration 每批一次；父取消等待子终态。

## 7. 阶段七：安全重试与形参声明（C10a、C10b）

### 7.1 C10a：工具声明的完整传递

`ToolMeta`（装饰器工具元数据）与 `ToolDefinition`（注册工具定义）同时增加 replay_policy、replay_contract_version。`tool(...)` 增同名关键字参数；`ToolMeta.build_definition()` 逐字段复制，不丢失声明。默认 NO_AUTO_RETRY；此阶段只标明纯数学和确认无写入的具体文件读取工具，不按模块全部放开。

同时新增 `side_effect: ToolSideEffect = UNKNOWN`（工具副作用声明枚举，定义于 common/tool_replay.py），贯穿装饰器、元数据、定义、恢复契约及调用记录。取值 NONE/PRESENT/UNKNOWN。声明由可信工具实现者负责，模型不能覆盖；与权限 policy、审批 needs_approval 分开。UNKNOWN 不允许 SAFE_RETRY；PRESENT 只有经提供方契约证明的 KEYED_IDEMPOTENT 例外，否则 NO_AUTO_RETRY。缺声明默认 UNKNOWN，不扫描函数名或 HTTP 方法猜测。

本轮内置声明表：math_calculate、read_text、list_directory、get_info、get_time 审核其实际路径无业务写入后声明 NONE；write_text、memory.write 声明 PRESENT；memory.read 因 `_get_memory_path` 会创建目录，按 PRESENT 保留现状；任意 shell 执行、未证明语义的外部搜索/天气调用、MCP 及旧自定义工具默认 UNKNOWN。NONE 不自动开启重试，仍须显式 SAFE_RETRY 与正预算。注册时不实际执行工具测试副作用。

追加按工具恢复参数，贯穿装饰器→元数据→工具定义→恢复契约→调用记录冻结快照：`recovery_max_retries: int = 0`（首次之外额外恢复尝试次数）、`recovery_initial_delay_s: float = 1.0`、`recovery_backoff_multiplier: float = 2.0`、`recovery_max_delay_s: float = 30.0`。次数非负且拒绝 bool；时间必须有限非负，multiplier 至少1，max_delay 不小于 initial_delay。未知工具和副作用工具默认不重试；SAFE_RETRY/KEYED_IDEMPOTENT 仍需预算大于零才可重试。注册不执行网络探测，不从模型参数接收这些字段。

调用记录新增 `recovery_retry_not_before: str | None`（UTC 最早允许恢复执行时间）；失败后按已累计恢复次数计算 `min(initial_delay * multiplier**retry_count, max_delay)` 并持久保存。恢复不能通过重启重置预算或提前执行；延时期间可取消，禁止持运行短锁睡眠。当前与冻结预算取更严格上限，契约版本变更仍阻断。正常请求层重试不消耗该计数，但须在工具契约中披露其上限，不能把两层计数混作一个“三次重试”。这些是当前具体设计建议，尚未声称用户逐字段确认。

`ToolExecutionContext`（工具执行上下文）新增 tool_call_id、attempt、idempotency_key。`ToolInvocation`（运行时工具调用输入）新增 attempt、idempotency_key；适配器构造上下文时还必须传 session_id，执行器 `_build_context` 复制全部身份字段和键，再注入 timeout/http_client。`FunctionToolHandler`（函数工具处理器）沿现有 ctx 参数注入，模型 schema 不得出现这些字段。

`ToolExecutor.describe_recovery(name)` 从注册定义读取策略与版本，未知工具返回 NO_AUTO_RETRY，不触发工具执行。`ToolExecutorAdapter.describe_recovery(call, execution)` 封装为契约对象；当前内置工具无 keyed 生产提供方，不自动声称支持 keyed。测试专用工具可提供有期限/无期限的真实去重契约。

### 7.2 修复结果分类信息丢失

当前执行器会把超时和异常转换为错误结果，适配器又转为普通 FAILED。仅增加“catch 超时”无法生效，必须修改数据契约：

- 新 `ToolExecutionEvidence`（工具执行证据枚举）放 `common/tool_replay.py`：`NOT_STARTED / RETURNED / UNKNOWN`。
- `tools/base.py::ToolResult`（底层工具结果）新增 `execution_evidence: ToolExecutionEvidence | None = None`；None 仅表示旧处理函数未声明，不能直接传到运行时。参数无效、策略拒绝、工具不存在等处理函数调用前失败设 NOT_STARTED；超时/抛异常/网络结果不明设 UNKNOWN。
- `runtime/application/dto.py::ToolResult`（运行时工具端口结果）增加相同字段，适配器显式透传。禁止只根据 is_error 推断执行已确定。
- 处理函数返回了网络错误但无法确认远端效果时，允许明确保留 UNKNOWN，执行器不能覆盖其证据。执行器固定归一化：正常纯字符串返回设 RETURNED；结构化成功且 evidence=None 设 RETURNED；结构化错误且 evidence=None 设 UNKNOWN；显式证据保留。明确可确认的业务错误由对应处理器标 RETURNED。适配器接收到仍为 None 的结果属于执行器契约错误，按 UNKNOWN 处理。这样既兼容已有正常成功工具，又不会把旧泛化错误误当可靠终态。

固定分流：COMPLETED 需要 RETURNED；FAILED+NOT_STARTED 或 RETURNED 可提交失败快照；FAILED+UNKNOWN 不提交确定失败快照，进入恢复判定；审批需求仍只挂起。成功标记却 UNKNOWN 视为工具契约不完整，保守停止，不虚构成功。

### 7.3 `_classify_call` 的算法

优先终态复用/失败收口、取消、审批、委派；仅 ordinary STARTED 无结果进入重试判断：

1. 当前策略与冻结策略必须相同、version 相同且非空；否则 BLOCK。
2. retry_count 达到冻结预算与当前预算的较小值则 BLOCK，错误码 TOOL_RECOVERY_RETRY_EXHAUSTED；预算零不执行恢复重试。
3. SAFE_RETRY → RETRY；KEYED → 必须键存在、冻结保证仍有效且当前契约未收紧到不可恢复 → RETRY；NO_AUTO_RETRY → BLOCK。
4. begin_attempt 在短锁内重读并再次检查资格，再增加 attempt/retry_count 并持久化；重试预算不能在内存先扣后丢失。
5. 任何重试都重新跑安全执行链，保留已批准同一调用的决议；DENY 不可绕过。模型不能修改策略和幂等键。

此版本的恢复重试只在显式恢复入口发生；运行中出现 UNKNOWN 先留下 STARTED 和持久诊断，返回未结束运行与工具错误，停止驱动，等显式恢复分类；NO_AUTO_RETRY 可立即 block_uncertain 失败收口。不得在 execute 内隐藏无限重试或重调模型。

新增 `record_interruption(run, call_id, evidence, error, checkpoint)` 只保存 STARTED 的最后证据、错误及 next retry time，通过同一投影协议提交；返回 control_status=recoverable。reconcile 全部分类先查 NO_AUTO_RETRY/无安全资格并报 TOOL_OUTCOME_UNCERTAIN，再对安全策略检查预算；不能把非幂等风险误报成“重试次数用完”。若硬崩溃没有记录 not_before，首次恢复以当前时间生成一次并保存，后续重启复用，不能永远后移。等待到期前不扣次数；到期后短锁内复查取消/契约/剩余预算，再 begin_attempt 持久扣一次。未知结果始终带 effect unknown，预算耗尽不能声称外部未执行。

有效调用契约必须包含函数参数默认值/校验语义与资源解析约定；replay_contract_version 由工具作者随这些变化提升。恢复时核对冻结的 workspace/policy 作用域，不允许相同相对参数重定向到新的工作目录；当前权限收紧可以拒绝，不能扩大原授权。KEYED 工具对相同键不同有效参数必须拒绝，不能依赖模型参数相同就忽略默认值变化。

实施细化（2026-11-12）：恢复契约与调用记录增加 `execution_scope: str = ""`，保存绝对 workspace 根目录及现有全局/Agent 规则、denied_paths、allowed_mcp_servers、network_services 的规范化 JSON 编码（键排序，枚举取值，不含凭据）。工具适配器传当前执行上下文，由执行器现有作用域解析生成。安全恢复时冻结值与当前值严格相等；不实现权限集合包含关系，任何规则变化均保守阻断，旧空值不获安全重放资格。此为落实原作用域约束的最小模型补充，不增加配置入口或文件。

实施细化：最大恢复次数取当前与冻结上限的较小值；退避参数变化保守阻断，不在恢复时重写冻结值。参数/策略预检明确 FAILED 且执行证据为 NOT_STARTED 或 RETURNED 时，保存可靠失败快照并进入现有失败策略，不能误记成未知效果。旧导入形成 UNCERTAIN 时也必须完成运行失败及检查点删除；工具阶段挂起状态的失败收口通过状态机处理。

**验收**：工具定义→元数据→适配器→上下文→处理器→模拟远端完整键链路；远端独立持久去重器证明同键重复请求只一次副作用。超时即使被底层归一化也进入 UNKNOWN；版本变化/键过期/预算耗尽阻断。只读重试可能返回新观测值，只有本地已确认结果才保证复用原值。

### 7.4 C10b：形参直接声明，由发现器生成校验模型与 schema

此 commit 是用户明确新增的注册体验改造，不是恢复协议的隐含必要条件。单独提交方便审查，但仍属于本 PR。现有 `_infer_args_model` 已支持基础标量签名推导，明确拒绝 Annotated/容器/可空类型；在其基础上扩展，禁止新增平行发现器。

**作者侧目标示例**（示例中的 ToolSideEffect 为副作用声明枚举、ToolReplayPolicy 为恢复策略枚举、ToolContext 为注入上下文）：

```python
@tool(
    name="builtin.files.read_text",
    description="读取工作区文本文件",
    policy=ToolPolicy.WORKSPACE_READ,
    side_effect=ToolSideEffect.NONE,
    replay_policy=ToolReplayPolicy.SAFE_RETRY,
    replay_contract_version="1",
    recovery_max_retries=1,
)
async def read_text(
    path: Annotated[str, Field(description="工作区文件路径")],
    *,
    context: ToolContext,
) -> str:
    # 此处沿用原文件读取实现，不改变路径授权与取消清理。
    ...
```

ToolPolicy（资源权限策略枚举）沿用已有类型；Annotated 为 typing 类型注解，Field 为 Pydantic 字段元数据函数。默认值放函数签名，例如 `limit: Annotated[int, Field(description="数量", ge=1, le=20)] = 5`；没有默认值才必填。`str | None` 没有默认值仍然必填，仅表示允许 null；写 `= None` 才可省略。

**首版推导范围与约束**：支持 str/int/float/bool、Literal、JSON 值枚举、list[T]、dict[str,T]、可空类型、这些类型的 Annotated 字段约束；支持命名参数及 keyword-only。支持嵌套 Pydantic 业务值类型，但禁止循环 schema；它不是工具顶层参数包装。拒绝 Any、未解析前向引用、仅位置参数、*args/**kwargs、任意实例类型及非可空的复杂联合；声明错误在发现时暴露。新形参声明不支持 alias/default_factory 或 Field 内的默认值，默认值以函数签名为唯一来源，冲突直接报错；现有 args_model 兼容路径不受这些新限制影响。

## 8. 阶段八：历史迁移、展示和交付验收（C11、C12）

### 8.1 C11：历史导入与读模型

恢复服务新增 `_import_legacy(run, checkpoint, messages, events) -> ToolCallLedger`，只在旧运行没有账本且没有新格式引用时调用。按源助手消息确定批次与顺序，绝不能仅靠剩余列表生成不完整账本。

匹配规则：真完成事件+其 result_message_id 对应消息+一致 call_id 可导入成功/失败；旧假审批终态只恢复等待；旧 consumed 必须找到同 approval_id 的 APPROVAL_RESOLVED 且 approved 为真实布尔才能恢复决定；孤立消息/开始无结果记 STARTED，由默认 NO_AUTO_RETRY 阻断。旧工具没有冻结版本，不能用今天的安全声明自动批准过去的重试。

导入通过 C05 一次保存账本与新检查点；旧磁盘消息/事件不重写。模型上下文必须使用新 `_filter_legacy_approval_results(messages, events) -> tuple[RunMessage, ...]`：仅过滤被旧假审批事件准确引用的消息 ID；不能按空内容删除真实空结果。过滤范围包括从活动 Context Version 重建的当前调用消息，不能只过滤 engine 的临时列表；源上下文含无法对应的假消息时拒绝恢复，不能把坏消息传给模型。

过滤后的列表仅供 Context Provider 输入，不能写回 messages.json 或用于重新分配序号；物理消息序号继续从未过滤事实取值。旧模型上下文内若存在正在等待的助手 tool_call，最终批准执行后必须补一条对应真实工具结果，保证模型协议配对；未结束批次不能先请求模型。已终态旧运行保持只读，不自动创建账本。对旧事件无法区分的失败无消息分支只可保守阻断，不伪造错误输出。

读模型修改：`_run_activity/_run_steps` 加入 TOOL_RECOVERY_BLOCKED，映射 uncertain；`RunStepResponse`（运行步骤响应）状态联合及 frontend types/api 校验增加 uncertain。`RunActivityPanel`（运行活动面板）显示“结果待确认”；运行终态仍失败，不新增一键重放按钮。`assemble_trace` 对新 attempt 用 attributes 记录多次尝试，对同调用只产生一个逻辑结果；审批只结束审批段；恢复阻断保留原因。

`RunObservation`（运行观察快照）若需读取账本，仅新增可选账本摘要，不把完整结果再次通过 SSE 推送；现有事件已足以展示的字段不增加第二个来源。固定选择：本 PR 展示仅消费事件与消息，不增加该观察快照字段。

**验收**：旧真假终态混合样本、旧 consumed、有结果无事件、空真实结果、活动上下文含假审批消息；均验证是否执行外部工具及最终模型收到的消息，不仅检查解析成功。前端 API 类型校验与展示同时通过。

### 8.2 C12：故障矩阵与合并条件

实现总设计第 9 节全部故障窗口，另补以下跨阶段组合：审批批准后工具外部成功但本地未存、取消到达工具投影半途、子结果投影半途父取消、旧数据导入半途重复恢复、同一运行连续两个工具批次。

v0.4 审查补充的必测窗口：工具事件原子替换前后；失败意图删除检查点后但 run 未更新；普通失败结果已存而运行未结束；拒绝决议已存而取消请求尚未生成；reserve 后 bind 前取消；完成批次后重启模型确实收到所有真实工具结果；真实安全链 ASK 与粗预检不同；recoverable/cancelling SSE 不冒充失败；空参工具传额外参数拒绝；旧审批消息过滤不回写磁盘也不复用序号。上述任一不通过不得宣称恢复闭环。

硬崩溃测试流程固定：测试父进程启动受测子进程 → 子进程通过故障点屏障报告到达位置 → 父进程终止子进程 → 新进程读取同一目录恢复 → 父进程检查独立外部计数器与存储事实。禁止把外部计数器放在被杀进程内，禁止仅靠抛普通异常模拟所有窗口。

| 检查项 | 合并门槛 |
|---|---|
| 已落账本结果 | 每个 call_id 一个逻辑结果，恢复不再次进入处理器 |
| 未知非幂等操作 | 外部副作用计数不因恢复增长，后续调用与模型未执行 |
| keyed 操作 | 键跨进程一致，远端副作用一次，本地结果一次 |
| 顺序与状态 | 事件连续、消息引用有效、每批 iteration 一次，等待不是完成 |
| 审批 | 未批准执行次数零，决议不翻转，不以 consumed 推断 approved |
| 取消 | 工具成功事实不被覆盖，资源与子运行未收尾不得提前结束 |
| 委派 | 稳定子 ID，A/B/C 不丢调用、不乱序、回调不重复结果 |
| 历史 | 旧假结果不进模型，新格式缺账本拒绝执行，错误不能被静默重置 |
| 工程边界 | 不新增并发调度、不增加数据库、不拆多个 PR、不改变无关评分定义 |
