# dotClaw Reliability & Benchmark Suite 初版方案

## 1. 目标与结论边界

本方案建立项目外围的量化评测能力，用可复现结果支撑简历中的工程成果：并发隔离、操作节点恢复、调用级工具安全、版本化上下文、多 Agent 委派，以及后续可从代码事实确认的核心能力。

它回答两类不同问题：

| 类型 | 问题 | 主要产物 |
|---|---|---|
| 正确性 | 相同业务任务是否按预期完成 | Eval 的 Case 断言、失败归因与 Trace 证据 |
| 量化对比 | 当前链路相对历史链路或后续版本的成本和可靠性如何变化 | 可版本对比的实验快照、统计报告和原始逐次结果 |

Benchmark 不进入 Runtime 主流程，不改变生产状态机、持久化语义或恢复逻辑。它调用隔离的主流程，再读取其结果和执行事实。

```text
Dataset / 可靠性实验场景
        ↓
当前或历史版本的隔离执行
        ↓
EvalResult + RunTrace / 历史 Journal 或调用记录
        ↓
统一结果与逐次原始数据
        ↓
统计、基线对照、README 与简历表述
```

## 2. 当前代码事实

- Eval 已有版本化 `EvalCase`、目录型 Dataset、`PlaybackRunner`、`ReexecutionRunner` 和 `RegressionReport`。
- Playback 强制冻结 Fixture 与严格匹配，用于确定性回归门禁；Re-execution 以当前 Agent/Prompt 重新执行同一 Dataset，仅供比较，不进入 Gate。
- `EvalResult` 已保留 `RunTrace`；Trace 可提供 LLM/Tool/Approval/Delegation Span、LLM 与工具耗时、失败工具数、不完整 Span 数和关键路径。
- 当前 Runtime 已持久化 AgentRun、RunMessage、RunEvent、ContextVersion、RunCheckpoint；上下文历史压缩为成功后提交的 Session 历史压缩候选。
- 当前 `benchmarks/` 是旧 Agent/Journal/ToolExecutor 微基准，不能直接作为 Runtime v2 结果协议；历史提交 `bdf0591` 仅用于验证历史 worktree 审计路径可行，不作为本套业务或效率对照的默认参考。
- 当前默认 pytest 收集并通过 872 项测试；项目尚未声明 pytest-cov 依赖，也没有统一的 unit/integration/fault/concurrency/performance marker 分类。

## 3. 核心交互与职责

### 3.1 Eval 与 Benchmark

| 层 | 所有者 | 职责 | 不负责 |
|---|---|---|---|
| Eval Dataset | `eval` | 保存审核后的业务任务、Fixture、断言与 schema 版本 | 重复执行、P95/P99 聚合、历史版本启动 |
| Eval 执行 | `eval` | 创建隔离 Run，判定任务是否完成，重建 Trace | 性能结论、跨提交对比 |
| Benchmark | `benchmarks` | 选择 Case、重复执行、故障/并发编排、采样、聚合、保存基线和对照报告 | 改变 Runtime 行为或替代 Eval Gate |
| 版本读取 | `benchmarks` | 将当前 Trace 或历史记录转换为统一指标 | 将历史字段强行迁入 Runtime |

常规的后续版本比较直接复用 Dataset：

```text
Dataset Case → Re-execution → EvalResult + RunTrace → Benchmark 聚合
```

历史版本没有 Eval/Trace 时，由 Benchmark 在 worktree 外围启动历史入口，并读取历史 Journal、最终结果或记录型外部依赖的调用日志：

```text
同一业务场景 → 历史入口 → 历史记录 → 历史版本适配
同一业务场景 → 当前 Eval → RunTrace  → 当前版本适配
                                      ↓
                              同一组基准指标
```

### 3.2 稳定结果协议（暂定实现）

`BenchmarkRecord`（单次实验记录）为 Benchmark 的唯一输入与原始证据，字段只表达跨版本稳定的语义：

- 实验标识：suite、scenario_id、case_id、attempt、seed；
- 版本与环境：git_commit、代码版本、Python、平台、配置哈希、数据集 schema；
- 语义结果：任务是否通过、终态、失败分类、断言结果；
- 成本：端到端时延、LLM/工具/审批等待/关键路径时延、LLM/工具调用数、输入/输出 token；
- 可靠性：恢复是否完成、恢复动作、重复 LLM/工具调用数、事实/Conversation/ContextVersion 不一致数；
- 安全与隔离：策略期望与实际决策、Handler 进入次数、乱序数、跨 Run 或跨 Session 串扰数；
- 证据引用：当前 Trace 或历史记录的路径/摘要。

`BenchmarkRecord` 不保存完整 Prompt、密钥或工具输出正文；原始持久化事实继续由 Runtime/历史版本所有。

`VersionAdapter`（版本读取适配器）只将一个版本的公开结果、Trace、Journal 或调用日志转换为 `BenchmarkRecord`，不参与主流程。每个适配器必须有固定历史样本的映射测试，防止 Runtime 字段重构造成静默的统计口径变化。

## 4. 第一阶段实验集

第一阶段优先形成能支撑简历的数据，不等待所有能力都具备。

| 实验族 | 执行来源 | 最小场景 | 主要结论 |
|---|---|---|---|
| 并发隔离 | 可靠性实验编排 | 同 Session 有序提交；多 Session 并行；取消不被排队阻塞 | 乱序数、串扰数、吞吐、P95、相对全局串行的变化 |
| 操作节点恢复 | 可靠性实验编排 | LLM 前、工具前、审批挂起、委派挂起、成功提交前的受控中断 | 恢复成功率、动作节点正确率、内部事实一致性、恢复 P95 |
| Capability 安全 | Eval Dataset + 工具 Fixture | 文件、命令、网络的 allow/ask/deny；审批与 Handler 屏障 | 决策正确率、deny 后 Handler 进入数、未审批执行数、策略链 P95 |
| Eval 业务回归 | Eval Dataset | 工具、审批、委派、上下文保持的已审核 Case | 任务通过率、失败归因、调用数、token、关键路径 |
| ContextVersion | Eval Dataset + 可靠性实验 | 重复构建、审批/恢复重放、成功/失败/取消后的摘要提交 | 哈希一致率、重放不一致数、Session 污染数、压缩 token 变化 |

多 Agent 取消传播、父子并发隔离和子 Run 完成后恢复窗口列入第二阶段；它们建立在第一阶段的并发与恢复实验设施之上。

模型熔断、供应商降级、运行中闭合片段压缩不进入当前承诺范围：前两者未确认是当前稳定主链，后者仍是设计方向而非现有实现。

## 5. 对比与统计口径

### 5.1 基线

- **后续版本基线**：当前提交以同一 Dataset/场景、环境、配置、种子和重复次数运行，提交 `BenchmarkRecord` 快照；后续提交直接对比。
- **历史业务基线**：由 PR2 的可复跑性审计为每个实验族选择语义相近、可独立运行的历史 Git 提交；不预设 `bdf0591` 或任何单一提交为唯一参考。历史版本不能执行的能力报告“能力不支持”，不伪造为 0 或性能百分比。
- **旧微基准数据**：未通过同一实验口径的审计前不得作为本套结果的比较基线，也不得与 Runtime v2 Trace 指标混合。

### 5.2 固定统计规则

- 成功率同时报告分子/分母与 Wilson 95% 置信区间；
- 安全、隔离、重复副作用等风险指标同时报告绝对错误数，例如 `0/1000`；
- 延迟报告 P50/P95/P99、最大值和样本数，预热样本不进入统计；
- 对比变化为 `(current - baseline) / baseline`，仅在机器、配置、任务和样本数一致时报告；
- 外部模型/网络路径标记为 `[EXT]`，不得与框架内部耗时合并；
- 外部 Tool 跨崩溃不承诺 exactly-once；仅报告观测到的重复执行，并将内部事实幂等性与外部副作用分开。

## 6. 首批 Case 与场景设计原则

Eval Dataset 的 Case 按业务能力建模，不按源代码模块或字段建模。每个 Case 必须有稳定的 case_id、成功断言、fixture、标签和 schema 版本。

建议首批标签：`tool-security`、`approval`、`delegation`、`context-version`、`recovery`、`concurrency`。

并发与故障场景复用相同任务语义，但单独声明并发度、故障点、触发条件、恢复动作和不可变量；它们不是普通单 Run EvalCase 的替代品。

## 7. 拟修改范围

本方案确认后再进入开发阶段；初步文件边界如下：

```text

  README.md                         # 改为可靠性与版本对照入口
  ...                               # 现有旧微基准保留为 legacy/micro benchmark
  reliability/                      # 并发与故障实验编排
  adapters/                         # 当前 Trace 与历史版本记录读取适配

tests/eval/                         # 仅补充经过审核的业务 Case/Fixture 测试
```

Runtime、状态机、生产持久化和生产恢复入口默认不改动。若实验发现缺失的权威事实，先以失败 Case 证明，再单独确认最小 Runtime 改动。

## 8. 分期与验证

1. **基线审计与结果协议**：选择每个实验族的历史提交；验证 worktree、依赖、入口和可读取记录；实现记录序列化、统计和映射测试。
2. **当前 Eval 驱动基准**：将现有审核 Dataset 接入重复执行与 Trace 聚合；生成当前提交的第一份可追溯快照。
3. **并发、恢复、安全实验**：实现受控调度、故障注入和记录型外部依赖；每个场景生成逐次 JSONL 与汇总报告。
4. **历史对照**：实现必要的历史读取适配，运行语义相同的场景；只对可对齐指标生成百分比比较。
5. **文档沉淀**：README 只列已经复跑的结果、命令与原始报告引用；简历措辞必须包含样本量、环境和适用边界。

每阶段至少执行目标 pytest、完整 pytest、基准协议测试、`compileall` 和 `git diff --check`。性能结果的正式基线至少 warmup 5 次、采样 30 次；故障/隔离率实验的样本量按置信区间目标另行确定。

## 9. 待后续确认

## 10. 已确认的开发顺序

### PR1：当前 Eval 基线快照

唯一目标：基于现有 Eval Dataset，重复执行当前 Runtime，并生成带原始逐次记录的可追溯基线快照。

PR1 的输入 Dataset 固定存放在 `benchmarks/datasets/runtime_core_v1/`，使用现有 `EvalCase` JSON schema 并由 Git 跟踪；不使用默认的 `data/datasets`，后者仍用于本地 Trace Draft 的生成和人工审核。

首批 Case 复用现有 Eval 测试中已经验证的 Fixture 语义，经人工审核后固化为工具成功、审批通过恢复、审批拒绝、上下文保持四个 JSON Case；不依赖本地真实 Run 自动生成 Draft。委派的提交、挂起与回灌仍由 Runtime v2 测试验证，留待 PR7 建立专用可靠性场景后量化。

PR1 只读取现有 `EvalResult` 与 `RunTrace`，完成 Case 选择、warmup、重复采样、统计、快照和报告。它不启动历史 worktree，不实现历史 Journal 读取适配，不实现并发或故障注入，也不修改 Runtime。

### PR2：历史基线可复跑与转换

唯一目标：先审计候选历史提交是否可在独立 Git worktree、该提交声明的解释器环境和显式历史源码路径中复跑；只有通过固定 `tool_success` 等价场景、能映射统一记录的候选，才冻结为旧 Runtime 主链基线并与 PR1 当前快照对照。

PR2 不迁移 Eval 到历史源码，也不把历史字段兼容逻辑加入 Runtime。历史测试是否存在或通过不是可复跑性的唯一证据；审计失败的候选记录排除原因，不产出性能百分比。只有语义相同、环境可复跑的共享指标才生成当前/历史对照；历史版本不支持的能力明确报告为“不支持”。

### PR3：并发隔离实验

唯一目标：经 `SessionInteractionService` 在受控负载下量化同 Session `accepted_seq` 对应的开始/完成/Conversation FIFO、跨 Session 的消息/事件/上下文/工具/输出隔离、取消不阻塞，以及相对 Benchmark 内部全局串行调度的吞吐与等待收益。

正式场景固定为同 Session 20 请求 × 100 轮、8 Session × 4 请求 × 100 轮、1/2/4/8 Session 扩展、长短混合负载和长 Run 取消 100 轮；全部使用固定延迟 Fake LLM 或 Fake Tool，保存环境、负载、原始 JSONL、快照和统计报告。`accepted_seq` 与全局锁均为 Benchmark 外围观察/对照，不进入 Runtime 生产语义。

### PR4：操作节点故障注入与恢复

唯一目标：在当前已持久化的 LLM、工具、审批和成功提交安全边界注入中断，分层量化正确操作节点恢复、内部事实幂等/最终一致性及外部副作用可能重复；以工具 checkpoint 已保存、外部副作用前的子进程强退作为代表性真实进程验证。

LLM 调用前失败与结果未知分别统计；工具执行后允许外部副作用重复被如实记录，但 ToolResult、状态迁移、完成事件和 Conversation 不得重复提交。委派等待冷重建当前是能力边界审计/预期失败，不进入正式恢复率；只有未来持久化父子关系、等待映射和结果回灌状态后才可升级。

### PR5：Capability 安全实验

唯一目标：以完整有限决策表量化参数校验、文件/网络/MCP 资源解析、allow/ask/deny、审批屏障、Handler 阻断、Agent 策略隔离和审计脱敏；以同一无副作用 Handler 的直接调用为基线，独立报告 validated invocation 至 Handler entry 的本地安全链 P50/P95 开销。

确定性正确性 Case 按完整表逐行执行，不机械重复；性能实验固定预热与多轮采样。路径结论只证明 Broker 决策资源与 Handler 执行资源对齐，不宣称解决校验后文件系统替换 TOCTOU。进程命令当前仅为 `process.exec` 档案级治理，未支持命令内容级细粒度约束。

### PR6：上下文与 ContextVersion 实验

唯一目标：量化固定输入的 ContextVersion 内容/Slot/消息一致性、`v1 → v2` 冷恢复抗漂移、GLOBAL/AGENT/SESSION/RUN Owner 隔离、当前 Session 历史压缩的 token/预算效果及成功/失败/取消/放弃污染边界；只覆盖当前已经实现的 Session 历史压缩，不宣称未实现的运行中闭合片段压缩。

PR6 以记录 Provider 加载/缓存事实为前提才报告复用效率，并以 Benchmark 强制重新加载外部 Slot 的反事实对照量化 `replay_active_context` 恢复阶段 P50/P95；该对照不属于生产 Runtime 路径。路径结论不涉及 TOCTOU，压缩结论不涉及摘要质量或真实回答质量。

### PR7：多 Agent 委派与证据收口

唯一目标：量化当前单进程委派的父子 Run 隔离、子终态结果回灌、父取消传播和多父 Run 并发串扰，并收口 PR1 至 PR7 的测试规模、覆盖率、README、报告和简历表述。

子终态 `completed`、`failed`、`cancelled`、`abandoned` 按完整有限结果表执行，验证父 Run 挂起、单次回灌、Task/事件/Conversation 语义及重复/未知子标识不产生额外子 Run 或回灌。父取消和 8 个并发父 Session 各重复 100 次，记录取消送达/父子生效时延、挂起至回灌 P50/P95、跨链路消息/上下文/工具/流式输出泄漏、错误投递、重复和遗漏。结论仅覆盖固定 Fixture 的当前单进程单层委派，不宣称跨进程等待恢复、远程/嵌套委派或外部副作用 exactly-once。

PR7 只接受已完成正式采样的 PR1 至 PR7 快照与 `pytest-cov` 结果，生成可追溯证据清单；每个对外数字必须关联固定 Git 提交、机器/环境、Dataset/Fixture、配置、原始 JSONL、快照和报告。覆盖率报告总体及 Runtime、Tool、Context、Orchestration、LLM 的真实行/分支覆盖率，不设阈值，也不以覆盖率替代可靠性结论。

PR3 至 PR7 都复用 PR1 的 `BenchmarkSample`、`BenchmarkSnapshot`、目录布局与统计规则；不得另建平行结果格式。模型熔断、供应商降级和其他未确认的稳定主链能力不纳入本轮 7 个 PR。

### [EXT]：真实 API 补充实验（按需启用）

真实模型/API 可用于确实需要供应商参与的端到端、流式或路由实验，但不作为 Runtime、恢复、安全、隔离等核心工程结论的必要前提。`[EXT]` 实验必须固定 Provider、模型、配置、地区/网络条件（可记录时）、样本量与成本信息；使用独立 Dataset、快照目录和报告，不与 Fixture 基准混合聚合。只有确认要回答“真实 API 下的端到端体验或调用稳定性”时才实施。

## 11. 已确认的实验治理规则

1. 开发期快速验证使用 `warmup=1, repeat=10`；正式 README/简历结果统一使用 `warmup=5, repeat=30`。并发、恢复与安全正确率实验至少执行 100 次或覆盖其全部有限场景。
2. PR7 加入 `pytest-cov`，如实报告总体与 Runtime、Tool、Context、Orchestration、LLM 的覆盖率；本轮不预设覆盖率阈值。
3. 只有固定提交、固定 Dataset/配置/机器、保存 JSONL 原始记录、快照可回溯并完成正式采样的结果，才能进入 README 和简历。开发期 quick run 只用于调试。
