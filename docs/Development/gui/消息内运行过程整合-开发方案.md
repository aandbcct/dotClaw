# 消息内运行过程整合：开发方案

## 1. 目标与边界

将接收提示、思考输出、工具步骤、执行详情、运行错误与审批操作放入当前请求的助手消息。完成后保留折叠的执行过程，正文突出显示。

- 复用 `run.accepted`、`message.delta`、终态 SSE 和现有 800ms 活动轮询。
- 后端只扩展 Web 活动投影；不修改运行引擎、模型驱动、输出端口、领域事件和磁盘数据格式。
- 不新增工具 SSE、自动重发、断点续传、进度百分比或历史思考持久化。
- 本页已收到的思考在完成刷新后保留；整页刷新后仅恢复现有持久化的执行记录。
- 未收到思考增量时显示“处理中”，不能伪造“思考中”。步骤时间顺序以后端事件序号为准。
- 当前文本 SSE 没有模型轮次标识：本次不承诺将每段思考精确插入对应工具前后；思考区域和有序执行步骤分别展示在同一消息中。

## 2. 后端模型与方法

文件：`src/dotclaw/channel/web/schemas.py`

新增 `RunStepResponse`（执行步骤响应模型）：

| 字段 | 类型／约束 |
|---|---|
| `id` | `str`，使用 `run_id:开始事件sequence`，轮询间稳定 |
| `sequence` | `int`，开始事件序号 |
| `kind` | `Literal["model", "tool"]` |
| `status` | `Literal["running", "completed", "failed", "cancelled", "approval_required", "interrupted"]` |
| `started_at` / `completed_at` | `str`，缺失为空字符串 |
| `call_id` | `str | None = None`，工具步骤关联现有工具详情 |

修改 `RunActivityResponse`（运行活动响应模型）：

- 新增 `steps: list[RunStepResponse] = Field(default_factory=list)`。
- 新增 `event_sequence: int = 0`，本次读取事件最大序号。
- 保留 `status/tools/error/approval_id/child_run_id` 等已有字段。

文件：`src/dotclaw/channel/web/app.py`

修改 `_run_activity()`，可提取私有 `_run_steps()` 辅助函数：

1. 按事件 `sequence` 排序；`llm_started/llm_completed` 配对为模型步骤，同一运行模型调用顺序配对。
2. `tool_started/tool_completed` 按 `call_id` 配对；保留并行工具的不同步骤。工具参数和结果继续放在 `tools` 中，不复制到 `steps`。
3. 工具审批保留 `approval_required`；成功的工具步骤不会因整个运行失败而改成失败。
4. 对终态运行仍未闭合的步骤：失败、取消分别映射对应状态；其余无法证明完成的情况标记 `interrupted`。不能永久显示运行中或补造成功。
5. 历史缺失开始事件时，使用可用完成事件的序号构造稳定步骤，开始时间为空；仅有旧 `tools` 的客户端数据允许降级展示。
6. 活动接口路径及权限、会话归属校验不变，不返回未经筛选的原始事件负载。

## 4. 前端方法修改

| 方法 | 必须修改的行为 |
|---|---|
| `send()` | 生成 `requestId`，建立 user/assistant 本地配对；助手立即显示 `sending`；保存原问题并设置 `activeMessageId` |
| `receive()` | 接收确认将 `run_id` 写入目标消息 `run_ids`；更新为 `processing`。思考／正文增量更新 `thinking/responding`；终态和错误写回同一消息，保留已输出文本 |
| `readActivity()` | 校验运行归属后写入 `activitiesByRunId`；按 `run_ids` 找消息更新。拒绝比缓存小的事件序号，并保留现有 revision、终态和跨运行保护 |
| `refresh()` | 按运行 ID 合并本地助手与服务器助手；迁移本地 `execution/reasoning`，同步 `activeMessageId`；仅移除已确定入库的本地 user/assistant 配对。保留未入库、失败及未知结果消息，不按文本去重 |
| `control()` | 增加目标助手消息 ID／运行 ID 参数；审批、恢复沿用原消息，禁止无条件创建 `local-control-*` 消息。重载后无消息载体时，仅为该运行建立一个占位载体 |
| `stop()` | 原消息显示 `stopping`；停止接口失败时恢复原阶段，错误写入这条消息 |
| `checkRunStatus()` | 增加可选目标运行 ID；查询失败落到目标消息，不能覆盖另一个当前请求 |
| 新增 `loadRunActivity()` | 按需加载历史运行，仅更新缓存和目标消息；不得修改当前会话运行阶段、活动指针或触发历史运行恢复 |

增加私有 `patchMessageExecution()`，统一在一次 `patch()` 中同步当前运行控制字段和消息视图；错误分支也必须使用，避免只有成功路径有反馈。

### 阶段优先级与乱序处理

- 确认终态、未知结果、停止、审批、恢复状态优先于文本提示；普通轮询不能把它们覆盖成“生成中”。
- `run.accepted` 重复到达不能把已收到文本的状态退回“处理中”。
- 同一模型步骤的 `running` 查询不能覆盖已收到的思考／正文阶段。
- 查询发现新模型步骤时，只有在查询发出后未收到新文本增量，才将旧文本阶段重置为 `processing`；用 Hook 内按消息记录的增量版本号比较，避免迟到查询回退新文本。
- 工具状态同样不得覆盖查询发出后收到的新正文；工具的真实状态始终显示在步骤列表中。
- 恢复连接后不能因为保留了旧思考文本就显示“思考中”；必须收到新的思考增量。
- `event_sequence` 相同不代表状态一定没变：允许更新断连后可恢复状态等非事件变化，但不得撤销已确认终态。

### 8.2 与方案的具体实现差异

1. 状态同步采用 `patch()` 内调用私有纯函数 `patchMessageExecution()`，而不是让每个分支手工维护两次更新；历史专用更新显式跳过当前消息同步，避免写错对象。
2. 除活动查询外，将已有终态 SSE 的状态、审批 ID 和错误同步到活动缓存。这样无需等下一次轮询才能显示审批/异常操作；没有制造新步骤或模型事实。
3. 第一次查询才看到模型步骤时，不直接覆盖已经显示的思考/正文；只有已有模型步骤被新的模型步骤替代，且查询发出后没有新增量时，才重置为“处理中”。这是对无法从文本增量确定模型轮次的保守处理。
4. 已经由 SSE 确认终态后，迟到运行中快照中的开放步骤按失败/取消/中断展示，不能以旧快照回退为永久运行中。仍不把没有完成证据的步骤标成成功。
5. `RunActivityPanel`（消息内运行过程组件）通过 `children` 接收原正文组件，使反馈排在正文下方；运行错误不再位于输入框外。历史记录的审批/恢复按钮禁用，实际调用还校验当前消息及运行 ID。
6. 原浏览器验收脚本中的旧弹窗、角标和“查看并决定”选择器已迁移到消息内过程；服务端历史夹具补上已有正式契约的 `run_ids`，不会通过相同文本猜测本地消息身份。搜索来源提示中的“执行详情”同步改为“消息执行过程”。
