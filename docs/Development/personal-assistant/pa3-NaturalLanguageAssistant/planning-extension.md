# PA-03 增量：事件记录与对话式计划

基线：`2a1999f`。2026-11-24 用户确认的本轮增量；与旧规格冲突时本文件优先。旧提交已完成，本轮不自动提交或推送。

## 总体设计

同一份正式事务供用户查看与助手查询；助手未结请求保存处理进度和规划草案，不建设第二套事务事实或通用记忆。明确属于用户的真实事件直接记录并告知；假设、举例、第三方事件不自动记录。先查已有相关事项，补答更新原记录。不完整时间保留原文和确定的日期，不猜具体时刻。事件时间不冒充截止。

已有事务增加 `planning` 对象：`kind=task|event`，`event_time`、`scheduled_time` 为现有 `{kind:date|datetime,value}` 时间结构或 null，`time_text` 为未丢失的时间原文，`related_task_id` 为关联事件 ID 或 null。使用领域 `TaskPlanning（事务安排）` 和 `PersonalTaskKind（事务种类）`；旧事务默认 task、所有时间空。事件不填写任务执行时间，任务不填写事件时间；关联对象必须是已有事件。日期可保存但不等于精确时刻。

`PersonalTask（个人事务）.planning` 用默认值兼容既有构造；服务 create/update 接收可选 planning，update 未传时保留原值。仓储将完整 planning 写入 SQLite 新列 `planning_json`，数据库 v3→v4 原子迁移，旧行默认空安排，原有事务、提醒、草案和回执保留。Web 原响应和输入增加 planning；旧调用不丢新字段。截止规则不变。

新增 `before_event` 提醒规则 `{kind,offset_minutes}`，仅允许明确到时刻的 event_time，事件改期同步计算、移除时间取消、时间已过暂停；作为一次性提醒处理。只知道日期或“晚上”时询问具体时刻。提醒不默认创建；用户明确安排才设置。完成/取消沿用原提醒联动。关联准备任务不自动重排。

规划复用 kind=create_task 的未结请求，payload 增加可选 `planning_stage=needs_input|drafting|proposed`，create intent 增加 `plan_items`（最多20个任务，每项 title/description/deadline/planning/reminders），selected_task_ids 关联已有事件。旧草案 JSON 仍可读。阶段不复用 Runtime 状态。

规划请求只能通过 plans.save 更新、plans.apply 完成或 requests.abandon 放弃；通用 requests.save 和单项事务/提醒动作不得用关联 request_id 修改或关闭规划请求。补充事件时间是独立事务更新，不携带规划请求引用。该限制保证一个事件更新不会提前关闭整个多事件规划；错误回执须给出具体的下一步工具与版本来源。

增加 `plans.save` 薄工具，接收可选 request_id/expected_version、summary、stage、event_ids、missing_fields、items；在现有请求保存流程中校验来源并关联当前输入，proposed 要求非空 items 且没有缺失项。新工具每个 item 必须提供 planning；event_ids 非空时，proposed 的每项 related_task_id 必须指向其中一个已确认事件。明确排定的日期/时段开始时间必须写 scheduled_time，结束/时长可写 description，不能只有文字排期；真正未安排的任务允许 scheduled_time=null。保存不会创建正式任务或提醒。`plans.apply(request_id,expected_version)` 从保存版本读取任务，只允许 proposed 草案；同一个 SQLite 事务创建所有任务、提醒、回执并关闭请求，保留原子性和稳定幂等键。用户对话明确接受当前版本后由模型调用；模型负责判断语言，程序保证对象/版本/状态和当前真实用户来源。修改草案后版本加一，旧版本不可执行。拒绝保留修改或放弃；不新增确认按钮。

所有内部助理工具默认自动可用：移除 batch.apply 的声明式人工审批以及服务层 approved 强制要求；prepare/apply 仍绑定持久提案和版本/hash，但不再要求同 run，不因普通运行结束自动撤销未执行提案。拒绝显式策略仍生效，不修改主干通用审批状态机。旧活跃审批仍可经原控制面收尾。旧 UI 预览兼容保留，不增加新确认控件。

工具查询与详情返回足够的真实字段（description/deadline/planning），不只给标题；提示词明确先记录事件、保存规划请求、继续澄清及对话接受后执行。自动读取有界未结请求，已有工具补充查询，重启不依赖聊天全文保留。

助理时间上下文增加基于原用户输入时间及业务时区的有界日期/中文星期对照，供模型解释周几，不用模型心算替代日期事实。模型规划需使用已知可用时段，避免准备任务之间重叠或占用已知事件时刻；发现冲突先修订同一草案。proposed 保存后回复须简洁展示实际安排的日期、时段及任务，不能只用笼统摘要替代待接受内容。本期不建设自动排程引擎，对语言理解和安排合理性的证据以真实对话检查为准。

用户现有事务页面作为计划列表，查询增加 `plan_filter=all|unscheduled|scheduled|ended`，默认 all；与既有 filter 相交，查询已结束时界面使用 filter=all。显示事件或任务、原文/精确时间、截止和关联事件；服务端筛选、排序和分页一致，不能只对当前页筛选。待安排=活跃事项缺少本类型时间（只有日期的事件仍可列已安排但显示待补具体时间）；已结束=completed/cancelled。时间排序以本类型安排时间优先，再使用截止与原稳定键。编辑保留安排字段并支持调整；不做日历、自动排程或后台持续跟进。

## 分阶段实施与验收

1. 数据与服务：个人事务模型/仓储/服务、提醒规则和 Web API。验证 v3 数据升级保留、旧更新保留 planning、时间语义、关联对象、改期/取消提醒、计划筛选与分页。
2. 助手闭环：模型/请求仓储兼容、计划工具、自动权限、查询字段及身份提示。验证草案无正式副作用、版本冲突不执行、对话关联、原子失败回滚、重放不重复、批量无需审批。
3. 用户列表：类型/API/现有页面与编辑，显示并筛选安排、关联事件与时间，保留普通事务能力；验证必要交互和构建。
4. 独立验收：以真实 Runtime/工具/SQLite 做创建事件→规划草案→修改→接受→正式任务→重启查询→明确提醒→事件改期/取消链路。使用当前真实模型补充原始两场考试对话，检查工具轨迹和数据库；逐项核对正式任务与被接受草案的标题、结构化开始时间和事件关联，不以只有任务行数或空字段彼此相等为通过。不以脚本模型证明自然语言泛化。隔离数据库和会话，不改正式用户数据。不扩修既有委派恢复缺陷。
